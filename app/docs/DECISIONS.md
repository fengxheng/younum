# 有数 YOUNUM · 技术选型与实现决策记录

> 本文记录与《安卓APP实现指南》的对应关系，以及**每一处偏离及原因**。
> 接力开发前请先读本文件与 `IMPLEMENTATION_STATUS.md`。

## 1. 技术栈：Flutter 取代 Kotlin + Compose（已与需求方确认）

指南 2.1 默认方案是 **Kotlin + Jetpack Compose 单 Activity**。实际采用
**Flutter 3.47 / Dart 3.13**，Kotlin 仅保留在 Android 平台侧（`MainActivity`）。

**原因**：需求方已配置好 Flutter 环境并要求用 Flutter 实现。

**影响与替换关系**：

| 指南要求 | 本工程实现 | 说明 |
| --- | --- | --- |
| Kotlin + Jetpack Compose | Dart + Flutter Widgets | 自绘全部界面，不套 Material 默认样式 |
| Room（外键 / 索引 / 迁移测试） | 待定：`drift` 或 `sqlite3`（阶段 2 决定） | 阶段 1 尚未引入数据库 |
| DataStore（主题 / 提醒 / 引导） | `shared_preferences` | 只存少量偏好，不存账单集合 |
| Coroutines / Flow / StateFlow | `Future` / `ChangeNotifier` + `InheritedNotifier` | 单向数据流一致；未引入 Riverpod/Bloc，减少依赖 |
| Hilt | 构造注入 + `InheritedNotifier` 作用域 | 仓库接口可替换的实现已就位（见下） |
| WorkManager | 阶段 6 用 `workmanager` 或平台闹钟 | 未开始 |
| SAX/DOM 解析 XLSX | 阶段 3 评估真机兼容后再锁定依赖 | 未开始 |
| Photo Picker | 阶段 4 用 `image_picker` / `photo_manager` | 未开始 |

**保留不变的约束**：金额用整数「分」、明确错误类型、UI → 控制器 → 仓库分层、
Compose 尺寸区间改读为 dp/sp、无障碍与主题规则全部沿用。

## 2. 图标：改用 Material 线性图标族

原型的 34 个图标是手写 SVG `path`（含 `A` 圆弧指令）。首版**不**自建 SVG 解析器，
改用 Material `_outlined` 图标族，原因：

* 指南 6.2 只要求「本地矢量资源或**一致的**图标库」，不要求逐像素还原；
* 自建路径解析器（尤其圆弧参数化）引入的调试成本高于视觉收益；
* 所有图标集中在 `lib/core/designsystem/younum_icons.dart`，替换为自绘矢量时
  只需改这一个文件，调用方零改动。

## 3. 字号：原型 9–10px 标注被整体上调

指南 6.2 明确「不得照搬网页画廊里 9px 的微小标注」。因此：

| 原型 | 本工程 | 用途 |
| --- | --- | --- |
| 9px `tiny` | 12sp `caption` | 辅助文案下限 |
| 9px `badge` | 11sp `badge` | 徽标 |
| 10px `muted` | 13–14sp | 次级正文 |
| 12px 正文 | 14sp | 正文 |
| 24px `h2` | 24sp | 页面标题 |
| 35px 面板金额 | 34sp | 面板金额 |
| 43px 卡片金额 | 40sp | 卡片核心金额 |

尺寸同理：横向留白 20px → 22dp，卡片圆角 20px → 20dp，控件圆角 10px → 10/12dp，
触控目标一律 ≥ 48dp（原型为 32px 的圆形返回按钮已补足点击区域）。

## 4. 文字缩放上限 1.6

`MaterialApp.builder` 里使用 `MediaQuery.withClampedTextScaling(0.85, 1.6)`。

**原因**：堆叠卡片是固定高度容器，2 倍字号下必然溢出。
**代价**：用户调不到 1.6 以上；**下限不压制**，缩小字号的能力保留。
**后续**：阶段 7 真机适配时应把卡片改为自适应高度并放开上限。

## 5. 分类图标注册表放在内存（阶段 4 落盘）

`CategoryRegistry` 已按目标形态实现「唯一图标来源」（指南 14.4.7）：
分类网格、分类管理、编辑器都从它解析。阶段 4 接入私有文件写入后，
把 `saveIcon` 换成「先写临时文件 → 原子替换 → 再提交数据库引用」即可，
调用方不变。

当前**不支持**上传图片：编辑器里「从图片选择」如实提示需等阶段 4，
不做假的上传成功。

## 6. 样例数据隔离与披露

`lib/data/sample/sample_data.dart` 里的数字来自设计稿（8,432.60 / 128 笔等）。

处理方式：

1. 文件头写明它是视觉样例，检索 `SampleData` 可列出全部待替换点；
2. 进入演示账本后，首页与月报显示可见的 **「示例账本」徽标**；
3. 逻辑未接通的页面显示 `YounumDemoNote` 说明条，写明「这里做的是什么、还没做什么」；
4. 账单内容（演示账本）使用指南 10.1 的 6 笔固定基准金额
   （$2800 + 29900 + 3650 + 12680 + 7800 + 6500 = 63330$ 分），便于阶段 2 直接对账。

## 7. 设计走查入口只在 Debug 构建

指南 1.3 禁止把设计画廊、侧边目录、手机外框复制进正式 App。
但 33 个状态需要一个高效核对入口，因此在 `kDebugMode` 下注册
`/design-review`，入口出现在「我的」页底部。

* Release 构建 `AppRoutes.isDesignReviewEnabled == false`，路由不注册、入口不渲染；
* 走查页本身只是**索引**，点进去是真实页面，不是静态截图。

## 8. 安全与隐私相关决策

* `android:allowBackup="false"` + `res/xml/data_extraction_rules.xml` 全量排除：
  与「仅本地使用」的承诺一致，不让账单被系统云备份静默上传（指南 8.3）。
* **未申请任何权限**，包括 `INTERNET`。因此「离线可用」不是降级，而是常态。
* 隐私页如实写明「应用私有存储不等于数据库已加密，本版没有实现加密能力」。
* 分享页的金额隐藏开关会**真正不渲染数值**（不是盖一层遮罩），
  这样阶段 5 接入 PNG 导出时文件天然不含金额。

## 10. 工程路径必须为纯 ASCII（已迁移）

工程最初位于 OneDrive 下的一个中文路径（`…\OneDrive\桌面\小项目\youshu`），
路径含中文且处于 OneDrive 同步目录内，触发了三类问题：

| 问题 | 实测现象 | 只靠配置能否绕过 |
| --- | --- | --- |
| Android Gradle Plugin 路径检查 | `flutter build apk` 直接失败，报 "Your project path contains non-ASCII characters" | 能（`android.overridePathCheck=true`），但只是关掉检查 |
| Dart analysis server | `flutter analyze` 报 `FormatException: Unterminated string`，进程退出 255 | **不能**，只能用 `dart analyze` 替代 |
| OneDrive 同步 | `build/`、`.dart_tool/`、`android/.gradle/` 中上万个小文件被持续同步，拖慢构建并造成文件占用 | **不能** |

**决定：迁移到 `D:\dev\younum`（纯 ASCII，且在 OneDrive 之外）。**

* 迁移方式：先在旧位置清理可再生缓存（`build/`、`.dart_tool/`、`android/.gradle/`），
  用 `robocopy /E` 复制（不用 `/MOVE`，避免中途失败留下半个工程），
  再用 SHA256 逐文件比对，确认 115 个文件全部一致后才删除旧目录。
* 迁移后 `android.overridePathCheck` 已删除 —— 不再需要绕过检查。
* 仓库根仍是 `younum/`，`设计稿/`（原型）与 `app/`（工程）保持同级。

**遗留隐患（迁移不能解决）**：本机 `sdkmanager.bat` 不可用，
调用时以 `NTSTATUS 0xC0000409` 崩溃。因此任何需要联网安装 Android SDK 组件的操作
（如补装 NDK 或新的 platform）都会失败。当前通过把 `ndkVersion` 显式指向本机已安装的
`30.0.16248370` 规避；后续若必须安装新组件，需要先修复该工具链或手动解压 SDK 包。

## 11. NDK 版本显式指定

`app/build.gradle.kts` 中显式写 `ndkVersion = "30.0.16248370"`，而不是用
`flutter.ndkVersion`。原因见上一节：Flutter 插件默认期望 `28.2.13676358`，
本机没有该版本，AGP 会尝试联网安装，而 `sdkmanager` 崩溃。

本工程与全部依赖都没有原生代码，NDK 只被解析、不参与编译，因此指向本机已有版本是安全的。
将来引入需要 NDK 的插件时，必须重新核对版本要求。

## 12. 固定语义色必须带不透明 alpha（踩过的坑）

`Color(int)` 按 `0xAARRGGBB` 解释。把六位常量直接传进去，例如
`Color(0xF5EBE0)`，alpha 会变成 `00`，元素**完全透明且不报任何错**。

这个坑一次性让示例账本徽标、所有分隔线、面板描边、图标底色、危险 / 警告色全部消失，
而且静态检查和测试都不会发现。

因此约定：

* `YounumColors` 里所有 `static const int` 固定色一律写成 **8 位 `0xFFRRGGBB`**；
* `ColorMath.toColor(rgb)` 做的 `0xFF000000 | rgb` 对已带 alpha 的值是幂等的，
  两种写法都安全；
* `YounumColors.allFixedColorValues` + `color_math_test.dart` 里的
  「固定语义色必须是不透明的 8 位 ARGB」用例防止回归；
* **主题派生色**（`raw` / `primary` / `soft` …）保持六位，因为它们要参与
  `ColorMath.mix` 与 `toHex`，只在渲染时经 `toColor` 转成 `Color`。

## 13. 卡片页纵向尺寸的约束

堆叠卡片是固定高度容器，卡片内容高度必须小于「卡片高度 − 2×竖向内边距」。
当前内容约 177dp（图标 40 + 间距 12 + 金额 46 + 间距 8 + 商户 20 + 虚线 33 + 底行 18），
可用 200dp，余量 23dp。

改 `transactionCardHeight`、`transactionCardPaddingV`、金额字号或商户行字号时，
必须同步核对 `TransactionCardView`，否则大字号下会溢出。

## 14. 阶段 1 走查后的两处 UI 调整（需求方提出）

### 14.1 月份入口改用矢量图标

首页与月报右上角的「9月 ⌄」原先把 `⌄`（U+2304 DOWN ARROWHEAD）当文字渲染。
该字形生僻，会落到系统回退字体，尺寸、基线与左右边距都不受控，
看起来又小又偏，与旁边的文字对不齐。

改为 `YounumIcons.expandMore`（Material `expand_more`，20dp）放进 `Row`，
`CrossAxisAlignment.center` 与文字对齐。这也符合指南 6.2
「图标使用本地矢量资源或一致的图标库」。

顺带把首页的 `PlainChipButton` 与月报的 `PlainLinkButton` 合并成
`PlainTextButton`（两边原本是几乎相同的两份实现，只差 2dp 水平内边距），
新增可选的 `trailingIcon`。

### 14.2 卡片手势提示行不再常驻

**这是对指南 14.1 的明确偏离。**指南要求「卡片下方**始终**显示
『← 左滑：稍后处理 / 右滑：确认已选分类 →』」。
需求方在阶段 1 走查时要求不展示，按本文开头的优先级规则
（用户最新要求 > 本文的明确业务规则）执行。

保持不变的约束：

* 手势本身**仍然生效**，语义不变（左滑稍后、右滑确认已选分类）；
* 拖动过程中卡片顶部仍实时显示「确认 · 分类 →」或「先选择分类」；
* 卡片下方的确认 / 稍后处理 / 撤销按钮都保留，手势**不是**唯一入口；
* 未选分类时右滑仍不提交。

`SwipeGuideRow` 组件保留未删，注释里写明了恢复方式（在 `CardsScreen`
把它加回卡片堆叠下方即可），便于后续改回来。

### 14.3 卡底提示注释也一并去掉

卡片下方原本还有一行「也可点按钮操作 · 未选分类时右滑不会提交」，
同样按需求方要求去掉。按钮一直可见，这行提示本来也是冗余的。

## 15. 卡片旋转的溢出必须预留空间

后层卡片靠 `Transform.rotate` 做出「一叠卡」的效果，但旋转会把矩形的**包围盒撑高**：

```
包围盒高度 = 高 × cosθ + 宽 × sinθ
超出量（上下各）≈ (高 × cosθ + 宽 × sinθ − 高) / 2
```

以 348dp 宽、236dp 高、6° 代入，单侧超出约 **17dp**。
最初的实现用 `Positioned.fill` 让后层铺满整个堆叠区且**未预留**这段空间，
旋转后的上角就直接压到了整理进度条上（阶段 1 走查发现）。

现在：`stackSwingReserve = 17`，堆叠区高度 = 卡片高 + 2×reserve，
三层卡片都从 `top: reserve` 开始排。改角度、宽度或卡片高度时，
必须按上面的公式重算这个值。

## 16. 性能：拖动热路径与转场

需求方反馈「拖动卡片」与「二级页返回动画」卡顿。定位到三类问题，均已修。

### 16.1 拖动时每帧重建整棵子树（最主要）

原实现把位移存在 State 的 `_dx` 里，`onHorizontalDragUpdate` 与动画回调都走
`setState`。真手指的移动事件频率可达 120–240Hz，意味着每秒上百次重建
`Stack` + 三层卡片 + 方向提示。

改为：位移放在 `ValueNotifier<double>`，阶段放在 `ValueNotifier<CardGesturePhase>`，
用 `ValueListenableBuilder` **只重建一层 `Transform`**；卡片内容作为常量 `child`
传入，完全不参与 rebuild。拖动过程中本 State 一次 `setState` 都不会发生。

### 16.2 每帧多做一次布局测量

`LayoutBuilder` 包装整个卡片堆叠，用于取宽度算提交阈值。
`LayoutBuilder` 会在布局阶段触发重建。改为拖动开始时从 `RenderBox.size` 读一次宽度
（反正边缘避让判断已经要读 RenderBox 了），彻底不用 `LayoutBuilder`。

同理去掉了外层单独的 `Listener`（只为记录起点坐标），
改用 `onHorizontalDragStart` 自带的 `globalPosition`。

### 16.3 每帧重新栅格化卡片

`Transform` 变化会让其子树重绘。给卡片内容加 `RepaintBoundary` 后，
拖动只更新变换矩阵，卡片（文字、虚线、描边）复用已有图层。

同时减掉两处重绘开销：

* 卡片去掉 `BoxShadow`：原型里的阴影只有约 3% 不透明度，肉眼几乎看不出，
  但模糊阴影在拖动 / 转场时每帧都要重新栅格化。
* 虚线分隔线从「一排 33 个 `Container`」改成 `CustomPaint`，
  减少几十个 RenderObject。

### 16.4 转场

根标签页的 `IndexedStack` 四项各包一层 `RepaintBoundary`：
未激活的标签不参与绘制，激活的那个缓存成独立图层，
从二级页返回（含预见式返回动画）时只需重新合成图层。

### 16.5 关于“用 debug 包感受性能”

上述优化之前，需求方感受到的卡顿是在 **debug 包**上评估的。
debug 模式下 Dart 是 JIT 解释执行、断言全开、没有 AOT 优化，
本身就会明显慢于实际发布形态。

**结论：判断性能请用 `flutter run --profile`（或 release 包），不要用 debug 包。**

## 17. 性能测量方式与局限（如实记录）

想拿帧数据时踩到的坑，供后续参考：

| 方式 | 结果 |
| --- | --- |
| `dumpsys gfxinfo <pkg>` | **不可用**。Flutter 用 `FlutterSurfaceView` 渲染，帧不计入该统计，全部返回 0 / 4950ms 哨兵值 |
| `dumpsys SurfaceFlinger --latency '<layer>'` | **无数据**。能匹配到 `SurfaceView[...](BLAST)#...` 图层并返回刷新周期（16666666ns = 60Hz），但帧时间戳为空 |
| `logcat` 中的 `Choreographer: Skipped N frames` / `HWUI: Davey!` | **可用**，作为粗粒度奇帧指标 |

**实际测到的**：在脚本化负载（10 次快速拖动 + 4 次二级页往返 + 4 次边缘返回手势）下，
**debug 与 profile 包都没有出现掉帧日志**，仅 2–3 条亚毫秒级的
`Frame time is 0.08 ms in the future`（vsync 时间戳提示，不是掉帧）。

**未能验证的**：无法用 `input swipe` 复现需求方主观感受到的卡顿。
脚本化滑动产生的是少数几个指针事件，而真手指以 120–240Hz 上报事件，
两者对「每帧 setState」这类问题的放大程度差很多。
因此 16.1 的修复是针对已定位到的机制，但**“改完就不卡了”需要真手指复测确认**，
本文不声称已完成该项验收。

如需真正的逐帧数据，需要用 DevTools 的 Performance 页
（`flutter run --profile` 后按 `P` 打开性能浮层，或从 DevTools 录制 timeline）。


## 18. 阶段 2：数据库选型（sqflite）与测试分层

指南 2.1 的默认方案是 Room（Kotlin / Android），技术栈换成 Flutter 后
必须选一个等价物。选的是 **sqflite**，不是 drift。

| | `sqflite`（采用） | `drift`（未采用） |
| --- | --- | --- |
| 类型安全 | 手写 SQL | 编译期校验 |
| 代码生成 | 不需要 | 需要 `build_runner`，改表就要重跑 |
| Android 侧 | 用**系统自带 SQLite**，零原生编译 | 需编译原生 SQLite，要 CMake + NDK |
| 本机风险 | 低 | 中 —— 本机 `sdkmanager.bat` 已崩过一次 |

取舍理由：**少一个原生编译环节就少一个坑**，而阶段 2 的验收重点
（金额守恒、跨月退款、分类合计守恒）本来就在业务函数里，不在 ORM 上。
代价是没有编译期的查询类型检查，用「显式 SQL + 行映射集中在一处」来补。

### 18.1 测试分层：为什么数据库测试必须上真机

`flutter test` 跑在 Windows 的 Dart 虚拟机上，用 SQLite 需要一个本机
**并不存在**的 `sqlite3.dll`（系统里只有给 UWP 用的 `winsqlite3.dll`）。
把系统 DLL 改名软链过去是机器相关的做法，换台电脑就红，因此不采用。

分层是：

* **纯 Dart 单元测试**（`test/`，秒级）：金额、分配守恒、退款抵扣、月度统计、
  会话编排、迁移框架 —— 全部业务规则。
* **真机集成测试**（`integration_test/`，`flutter test integration_test/... -d <设备>`）：
  外键、`ON DELETE RESTRICT`、唯一约束、`CHECK`、事务原子性、迁移不丢数据。

这样分不只是为了绕开环境问题：**外键与唯一约束只有真实数据库能证明**，
内存实现里的绿灯不算数。

## 19. 业务规则是唯一真源，SQL 只负责取行

月度净消费、分类净额、退款抵扣这些口径，如果各写一遍 SQL 聚合、
各写一遍 Dart 函数，迟早会出现「月报和明细对不上」。

所以：仓库按月份把相关记录一次读出来（`LedgerDataset`），交给
`lib/domain/rules/` 里的**纯函数**计算。好处是**单元测试里验证的公式，
和界面上跑的是同一份代码**。

代价是统计不在数据库里做聚合。个人账单的数据量远小于需要为此担心的规模；
真到需要时再按月份下推聚合，而不是现在就把公式拆成两份。

取数范围有个必须记住的细节：只查目标月份是不够的。**跨月退款**要求
额外把「关联到这些月份消费的退款」带进来（即使退款本身发生在别的月份）。

## 20. 撤销的保护：有关联退款时不允许撤销原消费

指南 3.5.6 / 3.5.7 要求原消费的拆分结构在有关联退款时不能直接破坏。
真机测试时发现一个**静默的错误**：撤销一笔已经被退款关联的消费，
会留下一个指向空分配的退款关联 —— 于是那笔退款去抵扣一笔**不再计入消费**
的记录，月度净额凭空变小，而且没有任何地方提示。

处理：`undo` 在动手之前先检查目标交易是否还有退款关联，有就
**明确拒绝并说明原因**（「请先解除退款关联再撤销」）。
先解除关联（退款恢复待核对），再撤销原消费。

这条规则最初被写成「靠外键 `RESTRICT` 挡住」，实测发现挡不住 ——
单分类消费的退款不需要 `refund_allocation` 行，所以没有外键引用那条分配。
**业务规则必须显式写出来，不能指望约束替它兜底。**

## 21. 卡片页只显示内置的一级分类

卡片页的分类网格放**8 个内置一级分类**，与设计稿一致；用户自建分类
通过「全部分类 ›」进入。

原因不是设计稿，而是布局约束：接入数据库后分类来自真实表，
自建分类（宠物、学习成长）会把网格从 2 行撑到 **3 行**，
把确认按钮与撤销 / 稍后 / 更多操作行**挤出屏幕**。
这在真机上一眼可见，违反指南 6.2「核心确认区尽量稳定可达」。

## 22. 首页区分「已导入」与「已确认归类」两个口径

`MonthlySummary` 里有两个数字，不能互相冒充：

* `importedExpenseCents` —— 本月账单里一共有多少支出，**不管整理到哪一步**。
  首页那张深色面板的「9月已导入支出」用它。
* `expenseCents` —— **已确认归类**的消费。只有它参与净消费与分类占比。

混用会出现两种错误：用前者画分类占比，会在没整理完时给出错误的比例；
用后者显示「已导入」，会在整理之前假装这个月没花钱。

## 23. 页面上不再有「视觉样例」数字

指南 1.3 点名了「网页中的 128 笔、¥8,432.60、环比、分类比例都是视觉样例，
正式页面必须来自数据库查询」。这一轮把**首页与整理页**换成了真实查询：

* 演示账本的 6 笔基准现在**真的写进数据库**（`DemoLedgerSeed`），
  首页的 ¥633.30 / 6 笔 / 2 个来源 / ¥503.80 / ¥129.50 全部是查询结果，
  并且正好等于指南 10.1 的固定基准。
* 账本里有没有记录不再用「是不是演示账本」近似，而是查出来。

**月报、趋势、明细、分享、我的**这几个页面在阶段 5 之前仍然展示样例数据
（`SampleData`），这一点如实记在实现状态文档里，不假装已经接通。

## 24. 「消费最少的一天」只看有消费的日子

设计稿样例里这个位置显示「9月7日 · ¥0.00」。那是因为原型的样例月份每天都有消费，
所以「最低日」看起来自然。

真实数据下大多数日子没有消费，于是「最低日」几乎必然是最早的那个空日子，
写出来是「9月1日 · ¥0.00」—— 正确但没有信息量。

因此**只在有消费的日子里比较**。这是刻意的偏离，理由记录在此。
如果以后要恢复「含空日子」的口径，改 `MonthInsights.lowestSpendingDay` 一处即可。

## 25. 「已导入」与「已确认归类」是两个口径

月度统计里有两个数字，不能互相冒充（第 22 节从首页的角度说过一次，这里是全景）：

| 数字 | 含义 | 用在哪 |
| --- | --- | --- |
| `importedExpenseCents` | 账单里一共有多少支出，**不管整理到哪一步** | 首页「已导入支出」、来源明细、月份页 |
| `expenseCents` | **已确认归类**的消费分配总额 | 净消费、分类占比、日均、环比、洞察 |

混用会出现两种错：用前者画分类占比，会在没整理完时给出错误比例；
用后者显示「已导入」，会在整理之前假装这个月没花钱。

## 26. 报告只有一个来源

首页、月报、趋势、明细、分享、月份页全都读同一个 `MonthReport`。

它是 `MonthReports.build` 一次算出来的：概况 + 洞察 + 趋势 + 有记录的月份 + 完整数据集。
好处是**「同一笔交易在所有页面金额一致」从源头成立**，而不是靠每个页面各自小心 ——
后者只要有人漏改一处就会破。

代价：每次提交或切月都会重算一次报告，比按需查询多一点开销。
演示账本只有 6 条记录，个人账本通常是几百到几千条，这个开销可以忽略；
真到需要时再按月份下推聚合，而不是现在就把公式拆成两份。

## 27. 趋势窗口保留空月份

近 6 个月的柱子按**连续自然月**排，没有记录的月份保留（柱子高度为 0，标签仍在），
而不是把空月份从窗口里挤掉。

否则「近 6 个月」在只有两个月数据时会显示成「近 2 个月」，
用户看不出中间断了哪些月份。数据库里没有记录 ≠ 那个月不存在。

## 28. 月份页加了跨年切换

设计稿只显示「2026 年」，没有年份切换。这在只有一个月数据时看不出问题，
但一旦用户跨年使用，2025 年的记录就**没有任何入口**。

因此在年份两侧加了「上一年 / 下一年」。这是为了不留下死路而做的最小补充，
不是设计稿要求的内容。

## 29. 导入先落暂存区，确认后才进正式账

`import_row` 与 `txn` 是**两张表**，不是一张。解析出来的行先写进
`import_row`，用户确认后才在**一个事务里**写入 `txn`。

理由是首页金额：如果解析结果直接进 `txn`，那么一份「映射还没核对完」的
文件就会污染首页的汇总。分开之后，「用户看到的金额 = 已确认的数据」
成为一个结构性事实，而不是靠界面上小心的提交时机来保证。

代价是多一次写盘（几百行规模完全可忽略），以及需要处理一个中间态：
进程在 `COMMITTING` 阶段被杀。`ImportStage` 因此带 `isInFlight`，
重启后可以识别出「上一次写到一半」的批次。

## 30. 撤回时按引用计数决定要不要删交易

`transaction_origin` 是交易与来源批次的**多对多**关系。

撤回一个批次时，只有**没有任何其它来源引用**的交易才会被删掉。
同一笔消费同时出现在微信和支付宝两份账单里是很常见的，
如果按「交易上记的 batchId」批量删，撤回其中一份就会连带删掉
另一份导入的同一笔消费 —— 而用户只是想把重复的那份退回去。

唯一索引建在 `(batch_id, row_number)` 上，因此提交过程重试不会把同一行
绑两次；否则引用计数会虚高，该删的交易反而删不掉。

顺带记录一个遗留：`txn` 表上有一个 v1 就存在的 `import_batch_id` 列。
它只能表达「最早是哪个批次发现这笔的」，**不足以**做撤回判定。
保留它是为了导入记录页展示，撤回一律走 `transaction_origin`。
没有删掉这一列是因为 `ALTER TABLE ... DROP COLUMN` 需要 SQLite 3.35+，
而 minSdk 26（Android 8）自带的 SQLite 是 3.19，会直接报错。

**第二条保护规则：用户整理过的交易也不删。**

引用计数只回答「这笔还被别的批次引用着吗」。还有一件同样重要的事：
用户可能在导入之后已经给它分过类、拆过分。撤回导入是退回「这次导入」，
不是退回用户在导入之后做的工作。

所以只要满足下面任何一条就保留并告诉用户，而不是静静删掉：

* 还有别的批次引用它；
* 已经有 allocation（分过类或拆分过）；
* `version > 1` 或整理状态不再是 `PENDING`（用户改过）。

`ImportRevert` 因此把「共享保留」与「已整理保留」分成两个列表，
因为它们是两句不同的用户可见说明。

**提交时的复用，比撤回时的小心更重要。**

同一笔消费被两份账单同时导入时，提交**不能**再插一条交易，
而要给已有那一笔新增一条来源绑定。否则：

* 真机上会直接撞 `(ledger_id, dedupe_key)` 唯一索引，**整批提交失败**；
* 即使插进去了，撤回时也判断不出引用关系，会把用户的钱删掉。

所以提交前会先按同源键查出库里已有的交易，命中的那些只绑不插。

**批次的生命周期**：已提交的批次不能当成暂存区直接删掉（会让交易失去来源
记录），必须先撤回；但**已撤回**的批次名下已经没有交易，可以直接删。
已撤回的批次也允许重新提交 —— 那是用户主动退回后又想装回来，
不该被幂等守卫当成重复提交。

## 31. 去重分「同源重复」与「疑似重复」两级，后者不自动排除

* **同源重复**：`命名空间 + 账户 + 稳定源交易 ID` 一致 —— 可以确定是同一笔，
  默认不纳入。
* **疑似重复**：只有商户、时间、金额相同，没有稳定单号 —— 默认**保留**并标记，
  交给用户逐组决定。

因为「同一家店同一分钟买两次」是真实存在的。把它当成重复自动删除，
是在替用户弄丢数据；而账单导入最不可接受的错误就是丢钱。

只有一份文件里有稳定单号时也不安全：不同账户下同一个单号不是同一笔，
所以去重键把「账户」也算进去。

## 32. 表头识别靠列名匹配，不靠固定列下标

判据是「这一行里有几个单元格能匹配已知列名」，而不是「第几行是表头」。

微信导出的前面有 6 行说明，支付宝更多，「另存为 CSV」还可能把列顺序改掉。
任何按固定下标取列的写法，在这些文件上都会静默错位 ——
最坏的后果是把备注里的数字当成金额，而界面上看不出异常。

必填列（时间 / 金额 / 交易对方）缺任何一个都**不猜**，进人工字段映射。

## 33. 「支出 + 正数」不是负号冲突

这是实现里真的踩到的坑：最早把两种写法都当成冲突，结果**整份微信账单
全部判为无效**，一笔也进不来。

微信与支付宝导出的支出行，金额都是**正数**，方向由「收/支」列单独表达。
真正矛盾的只有一种：「收入却是负数」—— 收入不可能写成负号。

判据改成上面这一条之后，负号只在两种情况下起作用：
方向列缺位时用来推断，以及识别「收入却是负数」这种真矛盾。

## 34. 文件选择手写平台通道，不引插件、不用 registerForActivityResult

指南 4.2 只要求一个能力：让用户用**系统选择器**选一份文件，然后读它的
`content://` URI。为此引一个第三方文件选择插件，就多一份要跟着
Flutter/AGP 升级维护的原生代码；而本机 Android 工具链本来就很脆
（`sdkmanager.bat` 崩、NDK 靠锁定版本）。所以直接写在 `MainActivity` 里。

**为什么用 `startActivityForResult` 而不是 `registerForActivityResult`**：
后者是 `ComponentActivity` 的 API，而 `FlutterActivity` 继承的是
`android.app.Activity`（从引擎 jar 里核实过，不是猜的），拿不到。
换成 `FlutterFragmentActivity` 就能拿到，但那要引入 androidx.fragment。
为一个文件选择动原生依赖不值得。代价是一个已弃用的 API 与一个共享的
`onActivityResult` 回调，所以请求码刻意取了一个不常见的值，避免与插件碰撞。

**包可见性是个真陷阱**：API 30 起，不在清单里声明 `<queries>` 的话，
`resolveActivity(ACTION_OPEN_DOCUMENT)` 会返回 null —— 明明系统里有
文件选择器，界面却会把「选择文件」判为不可用。已声明；同时真正能不能开
以捕获 `ActivityNotFoundException` 为准，不只依赖这个探测。

**元信息查不到不算失败**：`ContentResolver.query` 对没有 provider 的 URI
（例如 `file://`）会直接抛。最初写法让这个异常把整个读取带崩了。
现在文件名退回 URI 末段、大小交给「边读边挡上限」，读字节才是正事。

**顺手挡住的坑**：同时只允许一个选择请求。第二个请求直接拒绝，而不是
覆盖第一个的回调 —— 覆盖会让第一个 Future 永远不完成，界面卡在加载中。

**未验证**：用户真的在系统选择器里点一份微信账单。那一步需要人手点，
自动化点不可靠。所以真机验证的是「读出来的字节无损、能直接解析」，
而「用户点选」在 IMPLEMENTATION_STATUS 里如实列为未验证。

## 35. 来源命名空间由入口决定，不由用户再填一次

「选择账单来源」页有微信支付 / 支付宝 / 通用表格三条入口，它们**必须**把
各自的命名空间带下去：

* 微信与支付宝同一单号的记录**不是同一笔**，所以命名空间要进同源去重键；
* 如果三条路都写死成一个值，那么用户从任意入口导入的账单都会落进同一个
  「来源」，跨来源去重就在第一份真实账单上失真了。

这一条是界面走查时才发现漏掉的 —— 数据层一直支持，但没人把值传下去。
**「规则写好了」不等于「值真的传到规则那里了」**，这正是界面走查的价值。

顺带修掉一个死路：「通用表格」原先直接跳到字段映射页，而那时**还没有文件**，
用户会到一个无列可匹配的页面上。改成先去选文件。

## 36. 界面接线用 widget 测试守着，不靠走查

接线的典型故障不是逻辑错，而是**页面根本没接上**：按钮点了没反应、
跳转去错地方、数字还是样例数据。这类问题 `flutter analyze` 看不出来，
纯逻辑的单元测试也看不出来（它们从不构建 widget 树）。

所以导入流程有一个把**真正的 `YounumApp`** 挂起来、从首页一路走到提交完成的
widget 测试（`test/import_flow_widget_test.dart`），文件来源用假实现。
它当场抓出了三个真 bug：

1. 在 `didChangeDependencies` 里改会话状态 —— build 期间触发
   `notifyListeners`，debug 下直接抛「setState() called during build」；
2. 用户取消选择后解析页**永远转下去**：不定进度是无限动画，
   而 `idle` 被当成了「还在进行中」，于是既不停也不走；
3. 导入记录页在 build 期间读历史，同样的问题。

三个都是「能跑起来但用户会遇到」的问题。相比之下，人手走查一次只能覆盖
一条路径，而且下次改代码时不会自动重跑。

## 37. XLSX 自己读，不引电子表格库

微信与支付宝导出的是 `.xlsx`（zip + XML），不是 CSV。指南 4.2.5 明确要求
「不能未经验证就引入依赖桌面 Java API 的整个电子表格库」，所以 `xlsx_reader.dart`
只做需要的那三件事：用 `dart:io` 的 `ZLibDecoder(raw: true)` 解 DEFLATE、
一个够用的 XML 标签扫描器、Excel 日期序列号换算。**没有新增任何依赖。**

读出来统一成「与 CSV 一样的文本表格」，于是表头识别、字段映射、逐行标准化、
去重判断**一行都不用改** —— 下游不需要知道文件原本是什么格式。

几个不写就会踩的坑：

* 判断文件类型看**内容**（zip 魔数）而不是后缀名（指南 4.2.3）；
* 数字是日期还是金额靠**单元格样式**区分，判错的后果是日期变成一串看不懂的
  数字，而用户会以为账单坏了；
* 行号列号按 `r="A18"` 补齐（微信导出会跳行），否则用户拿行号回去核对会找错行；
* **不执行公式**（指南 4.2.5），只取缓存的 `<v>`；
* 样式表里全是自闭合标签（`<xf/>`），解析器必须处理，否则日期样式读不出来；
* 1900-03-01 之前的序列号要补一天。

## 38. 真实文件才暴露出「格式」这件事

整条链路此前都在仿造格式上验过，真实账单一下暴露三件事：时间存成
Excel 序列号而不是文本、金额带浮点尾巴、行号跳着走。

教训：**「解析器写完了」不等于「真文件能读」**。所以真实样本那一组测试
用文件**自带的汇总行**（「收入：2 笔 1.76 元」「支出：4 笔 3022.40 元」）
当断言 —— 这个期望值不来自我们自己的代码，比自造的期望值硬得多。

文件含昵称，已被 `.gitignore` 排除；样本不存在时测试**跳过**而不是假装通过，
这样别的机器上跑也不会假绿。（顺带修了 `app/.gitignore` 里把路径写成反斜杠的
一条规则 —— gitignore 只认正斜杠，那条一直没生效。）

## 39. 三屏引导：翻页距离为什么是 200dp 而不是一页宽

设计稿里引导一直是三屏，首版只做了第一屏，缺的两屏正好是产品最需要说清的
事（导入、月报）。补齐本身不复杂，坑在测试：

`PageScrollPhysics` 除了位移，还会把一定速度当成「甩一页」的补偿。
慢速拖**一页宽**（348dp）会变成翻两页；而 `tester.drag` 是「一帧内瞬移」，
速度极大，全被当成轻扫，小位移也会翻页 —— 那样测的就不是规范里说的
「不足 50dp 不翻页」了。所以测试用 `timedDrag` 慢拖、距离取 200dp：
算上补偿也只到 1 页，不带补偿也是 1 页。

规范的几条手感要求（首尾不循环、竖向滑动不翻页、小位移不翻页、
每屏都能跳过、前两屏「下一步」最后一屏「开启我的第一份月账单」）
都由 `test/onboarding_widget_test.dart` 守着 —— 这类问题
`flutter analyze` 看不出来。

## 40. 原型字号与无障碍下限冲突时，改盒子而不是改字号

真机上第 2 屏的「一次导入 · 开始整理」被折成两行，末行只剩一个「理」。
原因是原型的说明文字是 9px，而应用的辅助字号下限是 11sp（指南 6.3），
同一个盒子里放不下同一句话。

处理：**保留设计稿原文，把那张票据卡加宽**（`_MiniReceipt.width`），
而不是把字号降到 9 或把文案改短。加宽后卡片右侧会被前面那张盖住，
但文字到不了那么远，不会被挡。

## 41. 白屏先分清是应用还是环境

冷启动永久白屏时，logcat 里是 `Gralloc4: isSupported(...) failed`、
`Failed to allocate (4 x 4) ... usage b00` 这类图形缓冲分配失败，
**没有任何 `I/flutter` 的 Dart 输出**。这组合说明问题在渲染后端而不是 Dart。

用 `flutter run --no-enable-impeller`（Skia）一试即正常，于是定性为
设备端 Impeller/Vulkan 的问题，与本次改动无关。
**不要把它当成自己的 bug 去改 Dart 代码**；也不要默默在 Manifest 里
把 Impeller 关掉 —— Skia 已在弃用，那是产品决定。

## 42. 范围完整性多给一个入口，理由与位置

指南 3.4 说 `coverageConfirmed` 是「用户在**核对/完成时**确认」。原先只有整理
完成页有这个开关，看起来符合指南，实际有个洞：**只想看账的人不会走完整理流程**。
他们从月报页看到「部分账单」，却找不到任何能点的地方，于是环比、日均、分类变化
永远出不来 —— 功能做了，用户看不到。

所以月报页也给了入口，并且把「为什么只能算部分账单」拆成两种原因分开说：

* 还有记录没整理完 → 告知还剩几笔 + 「继续整理」（该去的是整理页，不是这里确认）；
* 整理完了、只差确认 → 「我确认 X 月账单范围完整」。

**两种原因混成一句话是错的**：用户会不知道该点哪里，甚至会在还没整理完时
去确认范围，把「数据完整」和「整理完成」两件事搅在一起。

确认前先弹一层问话。这不是多余的仪式：它是一句关于数据完整性的**断言**
（说出口之后日均按当月天数算、环比会出现），带副作用的断言不能一按就生效。

顺带修掉一个真缺陷：完成页的确认文案把月份写死成「9 月」，
用户切到别的月份再来完成页时，这句话与实际确认的月份对不上。
现在取当前会话的月份。

## 43. 拆分与「改性质」共用一条写路径

拆分与「重新归类」本质上是同一件事：**把旧的分配整体换成新的**。
所以没有为拆分单开一个 store 方法，而是把
`resolveTransaction({before, categoryId, ...})` 放宽成
`resolveTransaction({before, items, ...})`（一组分配）。

这样版本校验、会话顺序、撤销日志只写一次，两个入口（确认归类 / 拆分）
不可能出现「一边记得写撤销日志、另一边忘了」。改性质走的是另一个入口
（非消费不需要分配），但同样遵守这条：**一个事务里改状态、存会话、写日志**。

## 44. 「收到退款」没有放进性质页的单选里

设计稿的性质页有五个选项，其中「收到退款」在实现时是个陷阱：退款要
**关联到原消费**才算处理完成（指南 3.3/3.5），而那是**两笔**记录之间的事 ——
还可能跨月、可能部分退款、拆分过的消费还要指定退款分到哪些分配上。

把它做成单选里的一项，用户选了之后无处可选原消费，只能卡住（而且很容易
顺手确认成「一笔没有原消费的退款」，它去抵扣谁都不对）。所以本轮单选里
只有四种性质，退款关联跟着「关联一笔退款」那块单独做，详情页的入口文案
也相应改成「设为转账 / 收入 / 不计入」。

仓库层的 `setNature` 仍然支持 `refund`，但要求**已经存在关联**才允许 ——
规则放在数据层，将来哪个入口来调都一样。

## 45. 撤销要还原的不是「状态」，而是「那一组字段」

真机测试抓到一个单测没覆盖的 bug：撤销「改性质」只还原了交易性质，
**没有还原/清掉 `exclude_reason`** —— 库里会留下一条「性质是转账、
却写着一句为什么不计入统计」的记录，以后回看时没人知道那句话还算不算数。

根因是撤销目标（`UndoTarget`）里只存了 `beforeNature`，没存
`beforeExcludeReason`：**撤销能还原的字段，取决于操作前快照存了什么**。
补字段即可（撤销日志是 JSON，旧日志缺这个键就是 null，向后兼容）。

教训：新增一个会被改动的字段时，要同时问一句「它需要被撤销还原吗」。
内存实现与 SQL 实现都要改 —— 这个 bug 只有跑真机数据库测试才会露出来。

## 46. 「收到退款」最终还是进了单选，但带着一个条件选择器

第 44 条说「退款不能做成一个裸选项」，这一轮把它补齐了：选中「收到退款」
之后，同一页出现「抵扣哪一笔消费」选择器，没有选就不让提交（按钮灰掉并
说明原因），提交时走 `linkRefundAndResolve` —— **改性质与建关联在同一个
事务里完成**。这样第 44 条担心的中间状态（性质是退款、却没有连接）
在写入层面就不可能出现。

三个具体决定：

1. **候选是「本月的消费，除了这笔本身」**。退款只能抵扣消费（指南 3.5），
   所以候选里没有收入、转账、别的退款；自己也不是自己的原消费，
   直接从列表里去掉，而不是等用户选了再报错。
2. **拆分过的原消费明确拒绝，并说清为什么**。指南 3.5.5 要求退款指定
   「抵扣到哪些用途」，那个界面还没做。与其建一条抵扣不到具体用途的连接
   （会让拆分后的分摊金额悄悄算错），不如拒绝并提示先选别的原消费。
3. **这一步不写撤销日志**。退款解除关联是独立的能力（指南 3.5.7），
   还没有做，所以「撤销」在这里没有正确的语义 —— 与之对应，
   `RefundRules.validateLink` 的注释也写明：调用方是在同一个事务里
   完成改性质与建连接的。建立关联之后对原消费的撤销会被拒绝
   （真机测试覆盖），这正是「有退款时不能破坏原消费」那条规则。

跨月这件事在取数层解决：数据集同时覆盖退款月与原消费月，
真机测试证明上个月的消费也能被这个月的退款关联并落库。

## 47. `dataset()` 不给月份时，退款连接是空的

写这一块的测试时被绊了一下：用 `dataset(ledgerId: …)`（不带月份）断言
「连接建好了」，永远是 false。查下来不是 bug，而是两个实现一致的语义 ——
退款连接是**跟着原消费所在的月份**带出来的（跨月退款要算对就必须这样取数），
所以：

- 问某个或某几个月份时，`refundLinks` / `refundAllocations` 才有内容；
- 问「全部」时只返回交易。

两个风险都真实存在：调用方会误以为「全部」里什么都全，以及跨月连接的
原消费不在所查月份里，只看一个月的话连接也看不到。所以这个语义写进了
`LedgerStore.dataset` 的文档注释，测试里的辅助函数也注明「必须给月份，
跨月时两个月都要给」。

## 48. 解除退款关联：退款回到「不知道这是什么」

指南 3.5.7 要求「解除关联并将退款恢复待核对」。做的时候有两个容易含糊的
地方：

1. **性质回到 `unknown`，不是留着 `refund`。** 关联时把性质改成 `refund`
   是对的（那一刻确实知道它是退款）；解除之后「它到底是什么」重新变成未知：
   原始账单里那笔钱多半只是「收入」或一笔被退回的支出，性质是导入时按方向
   猜的，链接是用户后来加的 —— 两个都撒掉，让它在整理队列里等下一次判断。
   留着 `refund` 还有一个具体危害：它在整理页里看起来像一笔已经处理好的退款，
   而 `refund` 性质在没有连接时是提交不了的，用户会撞上一个说不清的状态。
2. **仍然是一次写入。** 与 `linkRefundAndResolve` 对称：删连接（连带
   `refund_allocation`）、改性质与状态、存会话，同一个事务。中间状态
   （「连接没了但性质还是退款」）和上次一样不能被看到。

另外两件在实现里才暴露出来的事：

* **撤回导入必须先断连接再删原消费。** `refund_link.original_transaction_id`
  是 `ON DELETE RESTRICT`，所以撤回一个「没编辑过、但被退款关联」的原消费时，
  不先断连接会直接报外键错误 —— 用户看到的是「撤不回去」；而内存实现是另一种
  错法：静默删掉原消费、留下一条指向不存在交易的连接。两个实现现在都在删除
  之前解除关联，并把结果放进 `ImportRevert.unlinkedRefundIds`，撤回弹窗因此
  能如实说「N 笔退款会解除关联并回到待整理（退款本身不会被删掉）」。
  这正是指南 4.4 那句「修复退款关联」的具体含义。

* **`refundLinkOf` 必须是直查，不能从数据集里找。** 数据集里的连接跟着
  **原消费所在月份**带出来（第 47 节），而这里问的是「**这笔退款**关联到了
  谁」—— 跨月时连原消费在哪个月都不知道，没法组月份集。所以存储层多了一个
  按 `refund_transaction_id`（有唯一索引）的点查；详情页也靠它把当前关联的
  原消费显示出来，否则跨月那个原消费会显示成「未知记录」。

## 49. 分类：数据库是唯一来源，图标按分类 ID 存

分类管理原来是**内存**实现（一份「名字 → 图标」表加一份自定义名字列表），
库里的 `category` 表只有种子数据。这带来两个真实缺陷：

1. **用户新建的分类只活在内存里。** 重启就没了；更糟的是整理时它**用不了**：
   归类要写真实的分类 ID，而那条分类在库里不存在 —— 界面敢列出来，
   写库时不认。用户看到一个「能选但不能用」的分类。
2. **图标按名字索引。** 指南 3.5.8 要求「重命名保留稳定 ID」，名字本来就不该
   当键：改一次名字，图标就找不回来了。

所以这一轮把分类改成「数据库是唯一来源」：`CategoryRegistry` 从 `category` 表
读，写也从它走（存储层只加一个 `saveCategory`，新建与更新共用它）。
顺带三个决定：

* **名称校验放进 `CategoryRules`**，界面与仓库共用一份。以前校验只写在界面里，
  而界面用的还是另一份样例列表 —— 会出现「界面说重复、库里其实没有」这种
  两套说法。同级重名依然由 `idx_category_parent_name` 唯一索引兜底。
* **改图标只改图标**（指南 14.3）：名称、ID、分类关系与金额都不动；
  存储层按 ID 更新，测试锁住「ID 与名字不跟着图标变」。
* **「恢复默认图标」要回出厂值**，所以它查种子里的定义
  （`CategoryRegistry.defaultIconKeyOf`），而不是库里当时的值 ——
  后者已经被用户改过了。

图片图标（`CategoryIconAsset` 与私有文件生命周期）仍然没做：界面上的
「从图片选择」如实说明这一点，而不是留一个点了没反应的按钮。

## 50. 拆分消费的退款：要「明确」，也要先有用途

指南 3.5.5：单分类消费退款直接抵扣该类；拆分消费退款要求明确退款分配
（合计等于退款金额，单项累计不超过原分配金额）。规则（`RefundRules`）
从阶段 2 就写好并有测试，但仓库层当时是**直接拒绝**拆分过的原消费 ——
能力在、用户走不到。这一轮把它接上，过程中做了四个决定：

1. **默认全填 0，不替用户分。** 指南要的就是「明确」：分错会让两个分类
   的净额都悄悄错，比让用户多点几下贵得多。界面上实时显示「已分配 / 剩余」，
   合计不对就不让提交。
2. **原消费还没有用途时，拒绝并告诉用户先去定用途。** 退款要抵扣到具体
   分类上，而「一笔没有分类的消费 + 一笔退款」加起来什么也算不出：
   连接建得起来，但抵扣不到任何地方。所以这里的不是技术限制而是语义限制，
   消息也写成下一步能做的事（「先去详情页给它定一个用途」）。
   副作用：**界面路径下，撤回导入不可能撞上「原消费被删但还有退款连着」**
   （有用途的记录撤回时会被保留）。撤回里那段先断连接再删的保护留着，
   因为低层 `linkRefund`（不带分配）仍然能建出那种连接，
   而且旧版本写下的数据也可能长这样。
3. **一行 0 不进草稿。** 规则层要求每一项都大于 0（“抵扣 0 元”没有意义），
   所以界面只把非零项传下去，「这一项不抵扣」= 不传。
4. **单项上限在界面上只按拆分项自己的金额算。** 已经抵过的额度（同一项被
   上一笔退款抵过多少）只有仓库层看得到（`RefundRules` 会算累计），
   界面看不到也不编 —— 真超了由仓库层给出原因。把已抵扣额度一并搬到
   卡片上是可以做的，但那是另一个改动，不搭这趟车。

落库那一步与关联写在同一个事务里：`refund_link` 插入后拿到它的 ID，
再把每一项写进 `refund_allocation`；`refund_allocation` 挂在连接上
（`ON DELETE CASCADE`），所以指南 3.5.7 的解除关联不需要额外写清理代码 ——
真机测试里跑了一遍，连接删掉后分配行为 0。

## 51. 分类图片资源：只存相对路径与哈希，不存「引用状态」

设计稿要求分类图标除了 12 个内置图标，还能用 PNG / JPG / WebP 图片
（最大 2 MB、1600 万像素，居中方形裁切）。这一轮先落地**数据层**：
`category_icon_asset` 表（v3 → v4 迁移）、校验规则、存储读写与真机验证；
选图与界面接线是下一步。

四个决定：

1. **只存相对路径。** 应用私有目录的绝对路径在升级、换设备、备份恢复之后
   都可能变；存绝对路径等于存了一个迟早会失效的东西。文件名用内容哈希，
   所以同一张图天然只有一份。
2. **不存「引用状态」。** 它等于「有没有分类的 `icon_key` 指向我」——
   存一份就会漂移。要判断时现算（清理孤立资源用得上）。
3. **同一哈希只留一条。** 唯一索引兜底，仓库层先查后写：重复选同一张图
   不会多一个文件，也不会多一行指向同一文件的记录。
4. **格式看文件头，不看后缀也不信 MIME。** 与指南 4.2.3 同一条道理；
   顺便把「非空、≤ 2 MB、≤ 1600 万像素」的判断做成纯函数，
   边界能穷举测试，而不是靠在真机上拿大图试。
   居中方形裁切的取整也做成纯函数（奇数差时两边各裁一半、向下取整），
   这类「差一个像素」的事在图片上肉眼看不出来，但会在小尺寸渲染时露馅。

顺带记一个 Kotlin 的坑：**块注释是可嵌套的**。我在注释里写了
`image/*` 这样的路径样式，其中的斜杠星号开了一层新注释，把后面整段代码
吞掉了 —— 编译器的报错指向很远的地方（`Expecting a member declaration`），
与真正的原因完全无关。注释里别出现斜杠加星号。

## 52. 图片图标的接线：先处理、再落盘、最后提交引用

指南 14.4.3 说得直白：文件与数据库**不可能**处在同一个原子事务里，
必须明确恢复与清理策略。这一轮把选图接上，顺序是：

1. **先处理**（解码 → 居中方形裁切 → 缩放到 256×256 → 重新编码成 PNG）。
   解码只走 `dart:ui`，不引图片处理插件：需要的就这四步，引擎本来就带得动。
   重新编码还有个附带好处 —— 原照片的 EXIF（拍摄位置之类）不会进到我们
   自己的资源里（14.3 要求去掉无关元数据）。
2. **再落文件**，文件名就是内容哈希，同一张图重复保存只有一份
   （库里的唯一索引兜底）。
3. **最后提交引用**：`saveCategoryWithIconAsset` 把「分类指向这张图」与
   「落这条资源」写在同一个事务里。

任何一步失败都**保持旧图标不动**，而且处理期间不删旧文件。只有替换成功
之后，才去看旧资源还有没有人引用 —— 没有才删（14.4.4）。删除顺序是
先删资源行、再删文件：反过来的话，中途失败会留下一条指向不存在文件的
记录，而那种记录会让渲染层每次都走一遍「文件不存在」的回退。

三个具体取舍：

* **选图只改草稿，按保存才提交**（14.3）。所以「处理成缩略图」与
  「落盘」被拆成两个动作：`prepareImage` 只做前者（草稿预览用，
  不落盘），`setImage` 才做全套。
* **连续选图只保留最后一次**：用令牌（`_pickToken`）把旧结果丢掉，
  慢的那次回来时不得覆盖新选择（14.3）。
* **新建分类 + 图片是两步**：先建分类（带草稿里的矢量图标），再换图片。
  这与指南 14.4.3 的「原子」不冲突 —— 那条讲的是**同一次图标替换**里
  文件与引用的关系；而「分类已经建好、只是图标没换成」是一个诚实的
  状态，用户能看到失败原因并重试，不会以为分类也没建成。
* **恢复默认图标要回出厂值**：查种子里的定义，而不是库里当前的值
  （后者已经被改过了）。同时把不再被引用的图片资源清掉。

渲染这一侧不用改：`YounumTileIcon` / `CategoryIconView` 早就支持
`imagePath` 并在 `errorBuilder` 里回退矢量图标（指南 14.4.8），
这次只是把路径真的传下去 —— 分类网格、分类管理、明细、月报、详情
五处都改成了从注册表取绝对路径。

**测试怎么切**（这一块折腾最久，值得记一笔）：真实图片解码在 widget 测试里
必须靠 `tester.runAsync` 推进，而 `runAsync` 里又不能放 `tester.tap`
（两边互相等，直接挂到 10 分钟超时）。所以「编辑器里选图 → 预览 → 保存」
这条界面路径没做成自动化，改成分三层验：

* `icon_asset_rules_test.dart`：纯函数的边界（格式、大小、像素、裁切取整）。
* `icon_asset_store_test.dart`：真的走引擎（生成 PNG → 裁切 → 落盘 →
  删除 → 清空），这里**可以**用 `runAsync`，因为没有界面在等帧。
* `category_image_test.dart`：编排与清理（顺序、失败不动旧图标、
  同一张图复用、替换时只删无引用的旧资源、两个分类共用一份资源时不能删）。
* 真机 `database_test.dart`：整条链路 + 重启后仍在 + 恢复默认清理。

界面那条路径记进了 `MANUAL_CHECKS.md` 的「已知未验证」，
不当作已验证。

## 53. 跨来源疑似重复：金额相同 + 时间接近 + 来源不同

指南 4.3 原来只规定了两种情况：**同源稳定单号相同**（可以自动判定为同一笔）
与**商户 + 时间 + 金额相同**（只能提示「疑似」，让用户逐组决定）。三份真账单
放在一起过的时候暴露了第三种，而且是最常见的一种：

> 微信、支付宝的扣款走的都是银行卡，所以**同一笔消费在两份账单里各有一条**。
> 可银行卡那份的「收款方姓名」写的是「支付宝（中国）网络技术有限公司」，
> 支付宝那份写的是真实商户名；时间也差几秒（下单时间 vs 扣款时间）。

按原来的规矩，这种重复**一条都发现不了**：商户不同、时间不同，弱键必然不命中。
结果是用户按提示把银行卡账单也导进来之后，同一顿饭被算两次，而应用一声不响 ——
违反的是「宁可少算，不要算错」。

所以加了第三级判定：

* **金额相同 + 时间相差 ≤ 24 小时 + 来源不同 → 疑似。**
* 它**只**产出疑似：行照旧 `newRow`、照旧计入、照旧能提交，只在提示文案里
  说清「和哪份账单的哪一笔撞上了、差了多久」，由用户决定。
  **绝不自动剔除** —— 指南 4.3 说了，跨平台金额相同不等于同一笔。
* 窗口取 24 小时，是故意取宽的：两份账单记的本来就不是同一个时刻，
  窗口放宽的代价只是「多问一句」，漏掉的代价是「算错一笔」。
* 同源键（命名空间 + 账户 + 稳定单号）仍然是**唯一**能自动判定的依据，
  这一条没有动。
* 手工记的账 / 示例数据没有 `sourceNamespace`，统一归一成空串单独算一类：
  空串只和空串同源，不会把两份真实账单当成同一份。

同一轮还发现银行账单的收支写的是**「转出 / 转入」**，原来的方向解析认不出来
（「转出」既不含「收」也不含「支」）。已补上这两种写法。

⚠️ 但**不要**把「交易类型」加进方向字段的公共别名表：微信账单里同样有一列叫
「交易类型」（值是「商户消费」这种），而且排在「收/支」前面 —— 一加就会把方向列
抢走，微信账单方向全错。银行卡要按**整套表头**做平台专用适配器。

## 54. 平台专用适配器：按整套表头认，别往公共别名表里塞词

三份真账单里，银行卡那份一直要人工映射。补适配器时踩到两个坑，都记在这儿。

**一、为什么不能把「交易类型」加进方向字段的公共别名表。**

银行卡的方向列叫「交易类型」（值是转出 / 转入），看起来往
`importFieldAliases[direction]` 里加一个「交易类型」就完事了 —— 但微信账单里
**也有一列**叫「交易类型」（值是「商户消费」这种），而且排在「收/支」前面。
列匹配是按列顺序扫的，谁先被认领谁就是方向列：一加，微信账单的方向列就变成
「交易类型」，整份账单的方向全判错 —— 还是**静默**判错（「商户消费」既不含
「收」也不含「支」，会被搁置成「待用户判断」）。

所以平台自己的列名只能挂在平台名下：

* `ImportPlatformProfile`：平台名 + 表头签名（`付款方姓名 / 收款方姓名 /
  交易流水号 / 账户余额`）+ 命中阈值（3 个）+ 自己那套「字段 → 列名」；
* 只有**整套表头对得上号**才启用它那套列名；公共别名表先跑，平台列名只补缺口；
* 宁可漏认（退化成人工映射，用户能自己指列），不可错认（静默判错方向）；
* 回归测试：`test/bank_statement_test.dart` 的「微信账单不会误用银行适配器」，
  断言微信账单的方向列仍然是「收/支」那一列。

**二、交易对方要结合方向取。**

银行卡明细里「付款方姓名 / 收款方姓名」两列同时在，而交易对方只有一侧：

* 转出（花钱）：对方是**收款方**；
* 转入（进钱）：对方是**付款方**。

不结合方向，转入那几行的交易对方会变成用户自己的名字。所以加了
`ImportField.payer` / `ImportField.payee` 两个字段，`parseRow` 按方向取；
微信、支付宝没有这两列，行为完全不变（仍然只看 `merchant`）。

顺带：「缺少交易对方」这项校验因此挪到了方向判定**之后**。校验顺序变了一点 ——
同时缺金额和交易对方时会先报金额。这更合理：金额都看不懂，方向无从谈起。

**三、平台名被数据行带偏（真缺陷）。**

`_platformOf` 原本从文件开头抓 6 行拼起来找「微信 / 支付宝」关键词，而银行卡账单
里有好几行的收款方写着「支付宝（中国）网络技术有限公司」—— 于是这份**银行**账单
被认成了「支付宝」。平台名只用于展示，但显示错了就是在骗用户。现在说明行只在
表头**之前**那几行里找。

> 这属于「只在真数据上才暴露」的那一类：造样例时不会往中间塞一行写着别家平台名字
> 的数据，可真实账单到处都是。

## 55. 导出：把「要画什么」做成纯数据，隐私开关才是文件层面的

指南 8.1 要求「分享开关必须影响最终文件，不是屏幕上的遮罩」，10.4 还要求
「隐藏金额后检查生成的 PNG，而非只检查屏幕遮罩」。这两句话指向同一个做法：
**别先画好再盖一层**。

所以月报海报分两步：

1. `SharePosterRules.build(...)` 按真实数据 + `ExportPrivacy` + 主题配色
   产出一份 `SharePosterSpec` —— 海报上要画的**全部**文字与颜色都在这份清单里；
2. 渲染器只有这一个输入，照着画。它没有别的数据源，也就画不出清单之外的东西。

好处是可验证：单测直接断言「清单里没有任何一行文字含那个金额」（连
`633` 这样的前缀都查），等价于「图里画不出那个金额」，不用对着 PNG 猜。
`showsAmount` 只作为渲染时的排版依据（占位符与真金额宽度不同），不承担隐私责任。

配套的几条决定：

* **默认不含商户、交易单号、身份信息**；连**用途名**也不放上去 —— 用途是用户
  自建的词（「医疗」「心理咨询」之类），默认不往外带最稳妥。海报只出现
  月份、金额（可关）、「N 笔生活记录 · M 种生活用途」。
* **每次进入分享都回到「隐藏金额」**，不沿用上一次的设置。上一次是私密发给
  自己，这一次可能是发到群里。
* **空月份不假装花了 0 元**：金额位置写 `—`，统计行写「这个月还没有记录」。
  与 3.4 节「空月份不能除以零、不能虚构环比」是同一条原则。
* 海报尺寸沿用原型的 750×1000（3:4），渲染时整体等比放大，不改版式。

CSV 那边是另一套：

* 列固定为 `时间,商户,金额,收支,用途,备注`，**数值列保持数字语义** ——
  支出写 `-28.00`，不写 `¥-28.00`，也不给负号加引号。
* **文本列**（商户、备注、用途）才防公式注入：以 `= + - @`、制表符或回车
  开头时前面加一个单引号。前导空格后跟这些字符也挡 —— `\t=` 在部分表格里
  同样会被执行。
* 加引号的规则还是 RFC 4180：含逗号、引号、换行才加，引号内部翻倍。
  验证方式是**把生成的 CSV 用自己的解析器读回来**，逐字段比对 ——
  自己生成的文件自己都读不懂，就别指望 Excel 读懂。
* 转账、排除统计、待判断**没有方向**，金额按绝对值写，不去猜是进还是出。
* CSV 只是数据导出，界面上**不写「备份」**：首版没有可恢复的备份格式，
  写成备份会让用户以为删了还能还原。

> 顺带清掉一处重复：交易性质的中文名原来在仓储层和月报页各写了一份
> （而且是会写进撤销日志的持久化文案）。现在收敛成 `TransactionNature.label`。

补记（同一天）：时间列最初直接复用了界面上的 `StatisticsTime.formatFull`，
出来是 `2026.09.19 11:16` —— 界面这么写没问题，但导出文件是要拿去对账、
甚至再导回来的：横杠加秒与各平台账单一致，Excel 也直接当时间认。
现在导出固定输出 `2026-09-23 18:09:20`，并写了断言锁住。
这条是界面测试抓出来的：测试里断言「每一行都是本月」，结果第一行就没通过。

## 56. 提醒：用 WorkManager，不申请精确闹钟权限

指南 8.2 要求「默认允许系统节电造成合理延迟，文案注明「约在此时间提醒」；
不为普通账单提醒申请精确闹钟权限」。这句话基本决定了实现选型：

* 用 **WorkManager**（`androidx.work`）排一个一次性任务，跑完自己排下一次。
  不用精确闹钟 —— 那是日历事件才需要的强度，换来的是不必申请
  `SCHEDULE_EXACT_ALARM`，界面上也就能理直气壮地写「约」。
* 唯一任务名 + `REPLACE`：用户改时间或关掉提醒都不会留下重复任务。
* 「同一个自然月只提醒一次」记在原生侧的偏好里，不依赖任务只跑一次 ——
  任务重试、系统重启后重新投递都不会重复打扰。
* 任务晚几天醒过来也照样发提醒：提醒迟到仍有意义，直接跳过反而像丢了提醒。

**两份日历推算，这是有意的。** Dart 侧 `ReminderRules.nextRun` 负责界面上
「下次提醒约在…」的说明（有单元测试），Kotlin 侧 `ReminderWorker.nextRunMillis`
负责任务自己续期（任务醒来时 App 不一定在运行）。两边都必须做短月顺延，
所以两处都把这个规则写得很显眼，改一处要记得改另一处。

**权限与状态。** Android 13 起通知是运行时权限（`POST_NOTIFICATIONS`），
只在用户主动打开开关时才申请。三条取舍：

* 权限被拒 → **开关回到关闭**，并说明原因。把开关留在「已开启」却发不出通知，
  比不显示更糟。
* 权限给了但用户在系统设置里把通知整个关掉 → 开关保持开启，但状态行如实写
  「提醒现在发不出去」，并指出到哪儿打开。
* 因此**没有**「再试一次」这类按钮：真正能解决问题的地方是系统设置，
  给一个按了也没用的按钮只会让人以为应用能自己修好。

通知点击只打开应用，不做深链：首页本来就会落在「需要整理的那个月」，
多传一个路由参数只多一处会失配的地方。

「清除本地数据」会取消提醒（账都清了，不该再收到「该整理上个月的账单」），
但**保留**用户选的日期与时间 —— 那是他的偏好，与账单无关。

## 57. 月报图片直接进相册；通知点开直接落到整理页

两条都是真机走查后改的。

**一、图片不再弹「保存到哪儿」。** 指南 8.1 写的是「保存文件使用系统创建文档流程」，
按用户要求改成：月报回顾直接写进相册 `Pictures/有数`，不再让用户选位置。
理由是它**就是一张拿来分享的图片**，多一跳没有意义；CSV 那种数据文件仍然走
系统「创建文档」流程自己选位置。实现上：

* Android 10 起用 MediaStore 写 `Pictures/有数`，**不需要任何权限**，
  写前标 `IS_PENDING`、写完清掉，相册就不会扫到半张图；
* Android 9 及以下没有分区存储，只能写公开目录并需要存储权限。那条权限用
  `maxSdkVersion="28"` 限住，新系统上不会冒出一个多余的敏感权限（8.3 的要求）；
* `DocumentSaved` 多了一个 `destination`，界面文案据此分清「已存到相册」
  与「已保存到所选位置」—— 不能一律说「已保存」。

**二、点通知要直接落到整理页。** 原来的通知只打开应用，落在首页；用户点这条
通知就是因为有事要整理，还得自己找一遍没有意义。现在通知带上一个路由提示，
应用启动或回到前台时取走它并跳转。两个细节：

* **冷启动**从启动 intent 取，**热启动**（应用已在后台）从 `onNewIntent` 取，
  两条路都要接；而且 `onNewIntent` 有时比回到前台晚一步，所以 resume 之后再
  问一次。路由**取走即清**，所以重复问不会多跳一页。
* 路由字符串**过白名单**：只认 `/organize/cards`，平台通道给什么就跳什么太危险。

**三、真机上抓到的预览 bug：品牌字样和月份叠在一起。**

海报预览用 `TextPainter`，只给了 `maxWidth`。段落宽度会缩到**文字自身**的宽度，
`TextAlign.right` 就没有可对齐的空间了 —— 右对齐失效，「∷ 有数」和「2026 / 09」
画在了同一处（导出文件走的是 `ui.Paragraph`，那里宽度由约束固定，所以是对的，
这也是为什么「功能没问题、只有界面难看」）。修法是把 `minWidth` 也给上：
右对齐时让它等于可用宽度。这条属于「只在真机上看才看得见」的那一类，
纯逻辑测试抓不到。

补记：真机走查又抓到一条 —— **从别处跳到一级标签页时，底部导航的高亮不跟着走**，
于是出现「人在整理页、高亮停在别的标签」这种自相矛盾的界面
（点通知进来就是这样；首页的「继续整理 →」也走同一条路）。

根因是 `TabSelection.syncFromRoute` **从来没被调用过**：只有用户自己点底部导航
才会换高亮。修法分两层：

* 给 `MaterialApp` 挂一个 `NavigatorObserver`，压栈 / 退栈时同步高亮。它只认四个
  一级标签，其余路由（详情、导入流程）不动高亮，避免误改；
* 退栈要**还原**压栈前的高亮：底部导航外壳里的选择才是「用户原本在哪儿」，
  压上来的标签页只是临时一层。所以观察者记下压栈前的索引，退栈时还回去。

另外，通知进应用不再用「压一层路由」，改成「回到根 + 切标签」：
整理本来就是一级标签页，压一层会多出一份同样的页面，退出时也会怪。

## 58. 进程被杀之后的导入恢复：按实际结果收尾，不猜

指南 10.2 要求「提交时进程结束后恢复不出现半批数据或重复记录」。
提交（`commitImport`）本身是一个事务，所以崩溃只会留下两种局面，
两种都必须**按实际结果**收尾，不能一拍脑袋：

* **事务还没开始就被杀** —— 批次停在 `COMMITTING`，库里没有这批交易。
  放回 `READY`，用户可以照原样再提交一次。
* **事务已经提交、状态没来得及改** —— 库里已经有属于这个批次的交易。
  必须补记为 `COMMITTED`。⚠️ 这一条是关键：如果也放回 `READY`，
  用户再提交一次就会入两份，正好撞上要防的那条要求。

判断依据是交易上的 `import_batch_id` —— 那个字段本来就是为「这批是谁导进来的」
存在的。所以恢复不靠信任状态字段，而是去问数据本身。

时机是**启动时**（`main.dart` 里 `initialize()` 之后扫一遍），扫全部账本。
失败不影响使用，只打日志：恢复是补救，不是关键路径。

测试分两层：单测 5 个（两种局面、已收尾的不动、撤销过的不动、无在途不动），
真机 2 个（直接改 SQLite 里的 `stage` 模拟被杀，确认 txn 笔数一笔不差）。

补记（阶段 7）：大文件那一组测试**当场抓到我自己引入的一个 bug**。

跨来源疑似重复原来是「按金额分桶」，加了大文件测试后发现同金额行一多，
每行都要扫一遍整桶（6 万行 × 同金额几百行 = 几千万次比较）。于是改成
「金额 → 来源」两层分桶，并且只取**别的来源**的候选 —— 大文件上省下的正是
「同金额行数 × 行数」那一项。

改完顺手把「桶里只有自己这一类就返回空」写成了「桶里只有一个键就返回空」，
于是「桶里恰好只有另一份来源」这种最常见的情况被整段跳过，跨来源检测直接失效。
`import_cross_source_test` 当场把它抓了出来。

教训记在这儿：**优化和功能是两件事，优化之后原来的功能测试必须再跑一遍**——
这次的顺序恰好就是先优化、再跑全套，才没有把它带到真机上。

## 59. 导入异常明细的导出：导的是完整清单，走「创建文档」

阶段 3 就记下了这一条，一直等到阶段 5 的导出能力就绪才动手。两个决定值得写下来。

**为什么导的是完整清单，而不是界面上那几十行。** 异常页面上只列前 50 行 ——
界面不负责承载一千行。但这个功能的用途恰恰是**让用户回原文件里逐条改**：
拿着 50 行的清单去修一份有 55 行问题的文件，最后 5 行永远修不到。
所以按钮交给导出的是 `session.invalidRows`（全部），而**不是**页面上那个
`listed`。这条差别界面上看不出来，只能靠测试守：界面测试里特意用 55 行坏行，
断言「页面上写着还有 5 行没列出来」而「文件里有 55 行」。

**为什么走系统的「创建文档」而不是相册。** 与月报回顾相反：回顾是拿来分享的
图片，再跳一次「存到哪儿」没意义；异常明细是**数据文件**，用户要放到自己能找到、
能拿去和账单对照的地方，位置该由他自己挑。保存结果依然是三态：取消不提示成功，
失败如实说原因。

列设计成 `行号,状态,原因,原始内容`：

* **行号**是用户在原文件里的行号 —— 没有它，几百行的账单里没法定位；
* **状态**用给用户看的说法（新增 / 重复 / 无效 / 已跳过 / 已导入），
  但「疑似重复」要单独说：它在库里仍是「新增」，直接照搬状态字段会误导
  （靠 `issue` 上的「疑似重复」前缀认出来，与重复分组用同一套判断）；
* **原始内容**是出事那一行的原文，方便在原文件里搜到它 ——
  这一列是**用户文件里的任意文本**，公式注入防护一视同仁，
  不能因为「这是导出给用户自己看的」就跳过。

文件名不带批次名：系统流程里用户自己就能改名，而批次名往往是
「微信支付账单(202609).xlsx」这种带括号的文件名，塞进去反而不好认。

## 60. 放开字号上限：让容器去适应文字，而不是让文字迁就容器

应用曾经把文字缩放**写死**在 1.6（`MediaQuery.withClampedTextScaling`），
注释里写的理由是「避免堆叠卡片这类固定高度容器在大字体下溢出」。

这个理由本身没错，但结论错了：它把容器的限制转嫁给了用户 —— 用户把系统字号
调到最大，应用却只肯放大到 1.6，等于替他决定了他能看多大字。指南 6.3 说得很
清楚：「不固定屏幕总高度。小屏和大字号时允许滚动」。

所以这次是把因果倒过来：**先让容器能长大，再放开上限**。

**卡片：设计高度是下限，不是高度。** `TransactionCardStack` 原来用一个写死的
`SizedBox(height: 236)` 把卡片框住，后层卡片也是同样的固定高度。现在改成
`IntrinsicHeight` + `minHeight: 236`：先问卡片内容「装下这些字最少要多高」，
设计高度当垫底。装得下时高度就是设计稿的 236（卡片内部的弹性空白把分隔线与
页脚推到卡片底部，视觉与设计稿一致）；装不下时卡片往上长，页面本来就
可滚动（`YounumScreen` 默认 `scrollable: true`），该滚就滚。

后层卡片从 `Positioned(height:)` 改成 `Positioned.fill`：层高由前层决定，
字号放大时三层一起长，不会露出半截。

代价是一次 intrinsic 布局（多一趟测量）。可接受：卡片只在换一张时重建，
拖动过程中只有 `Transform` 在变（这正是当初不用 `setState` 的原因）。

**金额：宁可缩，不可截。** 金额是页面里最大的字，大字号下最先横向顶出去。
`AmountText` 外面套了 `FittedBox(fit: BoxFit.scaleDown)`：宽度够时一点不动
（`¥633.30` 仍是设计稿那个大小），放不下才等比缩小。没有用 `ellipsis` ——
把金额截成「¥633…」比字小得多要糟得多，数字被截读出来的就是另一个数。

**首页头部：容不下就换行。** 「有数.」+ 示例标记 + 月份切换原来是
`Row` + `Spacer`。大字号下固定内容超过屏宽，`Spacer` 只能被压到 0，然后整行
溢出（360dp 屏 + 字号 2.0 实测溢出 16px，被新测试当场抓到）。改成两项的
`Wrap(alignment: spaceBetween)`：默认字号下仍是「左一组、右一个」，与设计稿
一模一样；装不下时月份按钮换到第二行，而不是被挤掉或把词标截断。

**验证。** 新增两组界面测试：

* `test/text_scale_widget_test.dart`：默认字号卡片就是设计高度；字号 2.0 时
  卡片**必须长高**（断言 `> 设计高度 + 40`，而不是「没报错就算过」）；
  字号 2.0 走一遍整理 / 月报 / 我的 / 本月四个标签页不溢出；窄屏（360dp）
  + 字号 2.0 金额缩得下。
* `test/card_swipe_widget_test.dart`：滑卡手势的回归。卡片高度改了实现方式，
  最容易悄悄弄坏的正是手势 —— 「滑了没反应」不会报错，只会让用户以为坏了。
  断言用的是**卡片换没换**（左滑是稍后处理，完成数不变，只看数字分不出
  「没反应」和「状态正确」），并且字号 2.0 下再验一次。

**仍未验证**：真机上系统字号调到最大、六套主题逐页对比度、TalkBack、横屏 ——
这些都只能人工走，见 `MANUAL_CHECKS.md` 第四节，不要当成已经验过。

补记（同一次改动）：**装饰插画里的字不跟着放大**。

真机把系统字号调到 200% 之后截图，引导页那两张小票据直接报了溢出
（`BOTTOM OVERFLOWED BY 101 / 40 PIXELS`，红色斜纹在屏幕上看得一清二楚）。
上限还写死在 1.6 的时候，这个问题被挡住了 —— 放开上限的第一件事就是把它

暴露出来。这也正是「先让容器能长大，再放开上限」这句话的另一半：
放开之前得先真的在各种字号下看过。

处理办法是把插画里那层文字缩放钉在 1.0：票据是**装饰**，不是内容 ——
它对读屏已经隐藏（`ExcludeSemantics`），尺寸、旋转角度与位置都是设计稿定死的
固定值，172dp 高的小盒子里还有虚线分隔与弹性空白，容不下任何放大。
试过 1.25（这台机器默认的字号），部件测试里仍然溢出；不同机器与 ROM 的字体
度量也不一样，留一点余量不够用。

真正的文案（英文小标、标题、正文）照旧按用户字号放大 ——
这里只是不把一张**图**当成正文来放大。

## 61. 首页右上角月份跑到第二行：带 `alignment` 的 Container 在有界宽度下会撑满

现象：示例账本首页的「9月 ⌄」掉到第二行、还居中显示，看起来像日期错位。

根因不在首页，而在 `PlainTextButton`：它的外层是
`Container(constraints: minHeight 44, padding: …, alignment: Alignment.center)`。
**带 `alignment` 的 Container 在宽度有界时会撑满父级** —— 这是 `Align` 的默认行为
（`widthFactor` 为 null 就尽量占满）。于是：

* 放在 `Row` 里时，非弹性子节点拿到的宽度上限是**无限**，`Align` 会缩到内容大小，
  所以一直看不出问题（三屏引导的「跳过」、月报页的「查看明细 ›」都这样用）；
* 放进 `Wrap` 时，子节点拿到的宽度上限是 **Wrap 的宽度**，它就直接占满整行，
  同一行的其它内容被挤到下一行 —— 而 `Container` 内部的 `alignment: center`
  又让文字在那条满宽的盒子里居中，于是出现了「跑到第二行且居中」。

首页头部那层 `Wrap` 是上一节为了大字号不溢出才加的，加的时候没意识到
子组件会撑满 —— **换布局时要连子组件的尺寸行为一起看**。

修法是回到根上：`PlainTextButton` 改成 `ConstrainedBox(minHeight 44) + Padding`，
宽度贴着内容。`Row` 里的用法行为不变（本来就是内容尺寸）。

**同类问题排查**：全仓 9 处 `Wrap` 的子节点逐个看过 —— 芯片、徽标、主题色块、
月份格子都是内容尺寸或显式给了宽度；其余 13 处带 `alignment` 的 Container 都有固定
宽高或在 `Row`/`Stack` 里，不受影响。只有这一处。

测试加在 `test/text_scale_widget_test.dart` 的「首页头部」组：字号 1.0 与 **1.25**
（这台机器的默认值，正是它会换行的那一档，单测默认的 1.0 反而看不出来）下
月份与词标必须同一行，且月份按钮的右边缘要与尾部入口的右边缘对齐；
2.0 下允许换行但不许溢出、不许压到词标上。

## 62. 发布签名：凭据不进仓库，也**不经过对话**

签名接到 `app/android/key.properties`，gradle 从这里读 `keyAlias` / 两个密码 /
`storeFile`。三条原则：

1. **凭据只在文件里。** 密码不写进代码、不写进提交信息、不贴进聊天 ——
   需要落盘时由我写脚本从密钥目录读出来写进 `key.properties`，
   脚本只打印「长度」不打印内容。key.properties 与 keystore 目录都在
   `.gitignore` 里。
2. **缺文件不报错。** 没有 `key.properties` 时回退到调试签名并在构建日志里说明，
   这样别人克隆下来、没有密钥也能 `flutter run --release`。代价是「看起来构建成功」
   不等于「签的是正式密钥」，所以 `RELEASE.md` 里写了怎么验：
   `apksigner verify --print-certs`，调试密钥的 DN 是 `CN=Android Debug,O=Android,C=US`。
3. **换签名等于换应用。** 调试签名的包与正式签名的包不能互相覆盖安装，
   从调试切到正式必须先卸载（数据一起没）。因此从这一版起日常试用也统一用
   正式签名的 release 包，`RELEASE.md` 里有命令。

顺带把 `namespace` 上那条「发布前确认包名」的 TODO 收掉了（包名确认属于上架检查，
`RELEASE.md` 的清单里还留着），`build.gradle.kts` 里原来 Apache 模板留下的
「Add your own signing config」TODO 也删了 —— 它已经没有意义。

## 63. 分类归档：把「删除」做成可逆的，就必须给出回来的路

指南 3.5.8 只有一句话：「分类删除默认归档，历史引用继续有效」。落到实现上要回答
四件事。

**1. 数据层早就准备好了，缺的是入口。** `category.archived` 字段、建表、读写、
以及「选择列表只取未归档」的过滤一直都在（因为它是从设计稿的字段表里直接抄下来的），
但**没有任何地方能把 `archived` 写成 true** —— 于是这个字段等于死代码。这次补的是
`LedgerRepository.setCategoryArchived()` 与界面入口。

**2. 界面上叫「删除」，语义上是归档。** 用户想的是「我不要这个分类了」，
所以按钮写「删除此分类」（内置分类写「归档此分类」—— 内置的不能删，只能收起来）。
确认弹层把两件事说清楚：

> 已经用它归好类的记录不受影响：用途、金额与月度统计都照旧。
> 变的只有一处：它不再出现在「选择用途」的列表里。想找回来时，在「分类管理」
> 最底部可以恢复。

**3. 有归档就必须有恢复。** 归档不做成不可逆的，就必须让用户找得到回来的路 ——
否则那个按钮就是陷阱：用户按下去，分类消失，历史记录里还写着它，而他不知道怎么找回来。
所以分类管理页底部多一个「已归档」区，列出归档的一级分类与「恢复」。

**4. 一级分类归档要连带细分用途。** 细分用途只能从父级进入，但「全部分类」页读的是
**扁平列表**——父级归档后它们会留在那里，成为「在选择里点不到、却还挂在列表上」的幽灵条目。
所以归档一级分类时把它的细分用途一起归档，恢复时一起恢复（跨层级的精细状态不做，
那是过度设计）。

**唯一被拒的情况**：最后一个还在用的一级分类不能归档 —— 用途列表空了，用户整理时
无从下手。`CategoryRules.validateArchive` 判断，界面**先把按钮置灰并说明**
（「这是最后一个分类，删掉就没有用途可选了」），而不是等写库失败再报错。这条与
名称校验同一条原则：界面与仓库用同一份规则，不会出现两套说法。

测试：规则 1 个、仓库 4 个（落库、**归档不动已有分配与统计**、级联与恢复、
最后一个被拒且不写库）、界面 3 个（删除→已归档→恢复的完整来回、内置只有归档、
最后一个置灰）。其中「归档不动已有记录」是这条需求的核心断言。

## 64. 在线升级：只碰一个公开的版本号

需求是「新版本从 GitHub Release 获取，走系统下载器 + 系统安装器，允许忽略某个版本
直到下一个版本再提示」。落地时有几个必须自己拿主意的地方。

**1. 联网边界要重新画，而且要说出来。** 在此之前，Manifest 里**没有任何网络权限**，
`RELEASE.md`、隐私页文案、设计走查清单里都拿它当「账单不出本机」的证据。加了
`INTERNET` 之后那句话就不成立了 —— 所以这次不是「顺手加个权限」，而是把承诺改成
仍然成立的说法：

> 账目数据不会离开这台设备；应用只会在你检查更新时联网
> （只读一个公开的版本号，再经你同意后下载安装包）。

改到的地方：隐私页文案、`RELEASE.md` 检查清单、`MANUAL_CHECKS.md` 第五节、
设计走查页里那条「本机处理，无网络权限」。**留着旧文案比没有文案更糟** ——
那是一句用户会相信的假话。请求头里只有 GitHub 要求的 `Accept` 与 `User-Agent`，
没有设备号、没有安装 ID、没有任何账单相关的东西。

**2. 只看 `versionCode`，不看 `versionName`。** 版本名可能改名、回退、带后缀，
拿它比大小迟早出错。所以 Release 的 tag 必须带 build number（`v1.1.0+2`），
解析规则放在 `UpdateRules.versionCodeOf`，认不出来就**如实说看不懂**而不是猜 ——
猜错的后果是给用户推一个更旧的版本。当前版本也不从 pubspec 抄，而是从
`PackageManager` 读：抄的那份迟早和真正装上的包对不上。

**3. 「忽略」的语义是「这一版我先不装」，不是「以后别告诉我」。** 所以忽略只记
一个 build number，出现更高的版本照旧提示；装上更新之后那条记录顺手清掉
（`UpdateRules.shouldKeepSkipped`）。忽略之后页面仍留着「下载并安装」的入口 ——
忽略不等于隐藏。

**4. 静默检查失败一声不吭。** 断网、被墙、限流、作者还没发过版本都是常态，
不能每次启动弹一句「检查更新失败」。所以 `UpdateController` 区分
「用户问的」与「启动时顺手查的」：只有前者才把失败原因显示出来。
更重要的是**绝不把「没查到」说成「已是最新」** —— 那会让用户以为自己在用最新版，
这条在规则与控制器的测试里各有一个用例守着。

**5. 最后那一下「安装」必须用户自己点，我们不装傻。** 所以：下载到应用私有缓存 →
FileProvider 给出 `content://` → 交给系统的安装界面 → 文案写「已交给系统，请在系统
界面点安装」，**不写「已装好」**（我们不知道结果）。「允许安装未知应用」这个开关
也只能用户自己打开，应用只负责把他带到那个页面。
`res/xml/file_paths.xml` 只暴露缓存目录下的 `updates/` —— 不写 `<root-path>`，
否则等于把私有数据全交出去。

**6. 几十兆要看得见在动。** 下载过程中从原生侧发百分比回来，界面上有进度条与
「已下载 n%」。转一分钟而屏幕不动，用户会以为卡死了。

**仍然未验证**：真机上的完整升级（下载 → 系统安装器 → 覆盖安装成功）需要
**先有正式签名的旧版本装着**，而这台机器上现在是调试签名的包 —— 见
`MANUAL_CHECKS.md` 第十五节，不要当成已经验过。

补记（同一天）：**预发布也要能读到，但只在没有正式发布时。**

用户建 Release 时勾了「pre-release」，于是 `releases/latest` 一直 404 —— 按定义它
**不返回预发布**。这不是接口的毛病，是「勾一个复选框」和「整条升级路径能不能用」
之间隔了一层没人告诉你的约定。

改法是在规则层加一条「从列表里挑」：`UpdateRules.readFromList` 跳过草稿、
跳过没有 APK 的，取 **build number 最大**的那条（列表顺序不是按版本排的，按第一条取
会读到旧版本）。调用顺序是：

1. 先问 `/releases/latest` —— 正式发布优先；
2. 它 404 时才退回 `/releases` 列表。

于是两种情况都成立：仓库里只有预发布时升级照旧能用；一旦发了正式发布，
预发布就不再打扰用户。命令行验证方式也留下了：
`flutter test test/manual/live_update_test.dart --dart-define=YOUNUM_LIVE=true`
（默认跳过，单元测试不该依赖网络）。真跑一次的输出是：

```
LIVE OK: 1.1.0+2 apk=https://github.com/fengxheng/younum/releases/download/v1.1.0%2B2/app-release.apk
```

**为什么值得留一个「手动跑」的测试**：单元测试里那份 JSON 是**我编的**，
线上那份是**真的** —— 字段名、嵌套方式、tag 里的 `+` 被编码成 `%2B`，
这些只有真跑一次才知道。

**更新页把发布说明当纯文本显示**（不渲染 Markdown）。2026-09-25 真机升级时看到
的就是这样：`##`、`**`、`>` 这些符号跟着正文一起显示出来了，读起来很吵。
所以发布说明要写纯文本（`RELEASE.md` 第 5 节已注明）。要做也应该是**渲染**它，
而不是让写的人去回避 Markdown —— 这条先留着，等真有别人用这个应用再说。

## 65. 数据库加密（方案 A）：口令由 Keystore 保管，文件搬成密文

需求是「数据库加密也要做」。落地时按方案 A（整库加密）做，不选「只加密几列」——
后者要重写所有建立在明文 SQL 上的搜索、筛选与分组，而且金额仍然明文，
代价大、收益小。

**两层结构，标准做法：**

1. 随机生成 32 字节**数据库口令**，交给 SQLCipher 打开数据库；
2. 口令本身用 **Android Keystore 里生成、永远导不出**的 AES 密钥做 AES/GCM 包裹，
   密文存 `files/younum.database.key`。

所以：把 `younum.db` 拷走没用（是密文）；连口令文件一起拷走也没用
（解密它需要 Keystore 里那把钥匙，它出不来）。代价必须讲清 ——
**钥匙丢了数据就永久读不出**，卸载、清应用数据、换手机都算。这条写进了
隐私页与 `RELEASE.md`，不是藏在代码注释里。

**几个刻意做成的样子：**

* **取不出口令时报错，而不是新生成一把。** 新口令打不开旧库，用户会在毫无察觉的
  情况下看到一个空账本 —— 那看起来就像账单被删了。宁可让隐私页明说
  「数据库没有加密：解不开数据库口令」。
* **迁移是「先留底、再搬、最后才删底」。** 老明文库改名成 `younum.db.plain`，
  新加密库走完整的建表 + 迁移链（所以老库停在 v1/v2/v3 也能搬），
  逐表搬完并**核对行数**，全部对上了才删留底。任何一步失败就删掉半成品、
  把留底改回来 —— 数据一条不少，只是这一轮没加密上。
* **中断会自动重来。** 启动时看到 `.plain` 还在，就认为上一次没搬完，改回来重做。
* **打开时就校验口令。** SQLite 是惰性的：不给口令去开一个加密库，`openDatabase`
  不报错，要等第一次真读表才炸。那样「口令不对」会以「某次查询失败」的形式出现，
  很难查 —— 所以 `onConfigure` 里主动读一次 `sqlite_master`。
* **FileProvider 只暴露缓存里的 updates/**，账单、图标、导出文件都不在内。

**验证（加密那 5 条真机用例全绿）：** 明文库搬完之后**文件头不再是 `SQLite format 3`**
（这是「真的加密了」最直接的证据）、账目与用户建的分类一条不少、留底已删、
正确口令能读、不给口令读不出、留底还在时会自动重来、已经是加密库时不重复搬、
全新安装什么都不做。

**踩到的坑记两条：**

1. sqflite 的工厂按**路径**缓存单个实例：迁移时已用正确口令打开过那个文件，
   同一进程里再用错误口令 openDatabase，它会把你那个连接直接还给你，
   压根不碰文件 —— 于是「口令不对」测不出来。测试里要换一个没被打开过的路径
   （拷一份）才是真的重新读文件。
2. sqflite 会把同一个原生异常**报两次**：一次回到 await 的 Future，
   一次落到 zone 的错误处理器上（会让测试莫名失败）。测试里用 try/catch 接住，
   不再用 `runZonedGuarded`（那个会把测试卡到超时）。

## 66. 分类合并：账目「迁过去」，源分类「归档」

指南 3.5.8 对这一块只有一句：「分类删除默认归档，历史引用继续有效。
重命名保留稳定 ID；**分类合并需显式迁移分配关系**。」—— 前半句归档已经做了，
后半句就是这一节。

**先说策略（需求方确认）：合并 = 把源分类上的账目迁到目标分类。**
不是「把源藏起来、统计时悄悄换算」，也不是「保留两个分类但显示成一个」——
`allocation.category_id` 真的改掉，因为只有这样，明细、月报、导出、
按分类筛选这些**已经写好的代码**才会一致，不需要各自打补丁。

**三件事，顺序有意如此：**

1. 校验（`CategoryRules.validateMerge`）：只能并到**同层级**的分类（一级对一级，
   细分对同一个父级下的细分）、目标不能已归档、源下面不能还有细分用途；
2. **迁移分配**（`LedgerStore.migrateAllocations`，一个事务）；
3. 源分类**归档**（不是删除）。

迁移在前、归档在后：万一归档这一小步失败，用户看到的是「账已经并过去了，
那个空分类还在」—— 比反过来（分类没了、账没动）好解释得多。

**为什么「只能同层级」：** 把一级分类并进别人的细分用途，迁移之后那笔账会挂在
别人的子节点下，用户根本找不到它；反过来把细分提成一级更没法解释。
跨层级不是被技术禁掉的，是语义上说不通。

**为什么「源下面还有细分用途就拒掉」：** 合并只迁移**直接挂在源分类上**的分配。
子分类的账不会跟着搬（它们本来就属于别的分类），结果会变成「一堆账挂在一个已经归档的
父级下面」。与其默默把账藏进角落，不如让用户先把子级处理掉（归档或合并都行）——
把话说清比替用户猜强。

**为什么放在存储层：** 这件事在 SQL 上有两个真实的坑，只能在事务里解决：

* `allocation(transaction_id, category_id)` 上有**唯一索引**。同一笔交易同时拆给了
  源和目标时，直接把源那行的 `category_id` 改过去会撞索引 —— 必须先把两行金额
  合到目标那一行，再删源那一行。金额只相加、从不改动，因此「分配合计等于原金额」
  （指南 3.5.1）仍然成立。
* `refund_allocation.original_allocation_id` 是 **ON DELETE RESTRICT**，
  而它指的是**具体的拆分项**。删掉源那一项前，要先把指向它的退款分配改指向留下来
  的那一项；两边都已经指向同一个关联时金额相加（合计不变，所以
  「退款分配合计等于退款金额」「单项累计不超原分配金额」仍然成立，指南 3.5.5）。

不撞车的大多数情况就简单了：`UPDATE allocation SET category_id = ?` ——
**保留行 ID 的改动**，退款分配指的本来就是它，不需要动。

**不提供撤销。** 撞车时分配的行结构真的变了（两行合一），撤不回去。
所以界面的确认弹层里写明了「这一步不能撤销」—— 这是用户敢按下去的前提。

**代价与边界（已知）：** 合并会让「这笔退款当初是抵在哪个拆分项上」的信息变粗
（变成了目标分类那一项）。这是合并语义本身带来的，不是实现偷懒。
另外，撤销历史（`review_action`）里存的是旧的分配草稿：合并之后再去撤销一条**旧**操作，
分配会按当时记录的 `categoryId` 回来 —— 也就是会重新指向已经归档的源分类。
记录仍然正常显示（归档分类保留身份），这里没有额外处理。

## 67. release 包启动即崩：R8 把反射构造裁掉了

**现象很误导人**：`flutter build apk --release` 装到真机上，点开图标**什么都没发生**
—— 没有白屏，没有闪退提示，直接回到桌面。`pidof` 查不到进程，logcat 里一条
`flutter` 日志都没有（因为崩在 Flutter 引擎起来**之前**）。

真凶在 `AndroidRuntime` 那行：

```text
FATAL EXCEPTION: main
java.lang.RuntimeException: Unable to get provider androidx.startup.InitializationProvider
Caused by: java.lang.NoSuchMethodException: androidx.work.impl.WorkDatabase_Impl.<init> []
    at androidx.work.WorkManagerInitializer...
```

Room 生成的 `WorkDatabase_Impl` 是**反射**实例化的（`Class.getDeclaredConstructor()`
+ `newInstance()`）。R8 做静态分析时看不到这个调用点，就把那个无参构造当成死代码删了。
而 WorkManager 是通过 `androidx.startup` 的 ContentProvider 在**进程启动时**自动初始化的，
所以这个崩溃发生在最早的阶段，任何 Dart 层的日志都没机会输出。

**为什么只有 release 会炸：** debug 不跑 R8。`flutter analyze` 也看不见
（那只管 Dart）。所以：**改了原生代码或依赖之后，必须用 `flutter build apk --release`
真机启动一次**，只跑 debug 等于没验。

**修法：** 新增 `android/app/proguard-rules.pro`，在 `build.gradle.kts` 里给
release 显式写上 `isMinifyEnabled = true` + `proguardFiles(...)`，规则两条：

```proguard
-keep class * extends androidx.room.RoomDatabase { <init>(); }
-keep class * extends androidx.work.ListenableWorker {
    public <init>(android.content.Context, androidx.work.WorkerParameters);
}
```

第二条同样重要但**不会当场炸**：`ReminderWorker` 也是按类名从数据库里读出来反射构造的，
被裁掉或改名的话，每月整理提醒只是**静默失灵** —— 更难发现。

**顺带纠正一条之前的判断。** 之前把「真机白屏」记成了本机 Impeller 的问题。
这一轮在同一台机器上做了对照：同一个 APK 用普通 `am start` 启动（Impeller 开着）
**画面完全正常**，`--no-enable-impeller` 也正常。所以白屏不是 Impeller；
那一轮的 logcat 里同时有 `MainActivity EXITING` + `DeadObjectException`，
更像 MIUI 在那次安装/启动时把 Activity 掐掉了。结论已按实测改写，
不再把它当成渲染后端的问题。

### 事后补记（同一天）：**线上那个 `v1.1.0+2` 本身就是坏的**

要验「旧版能升级到新版」，就得先在真机上装一个**能跑**的旧版。
于是把线上 Release 里那份 `v1.1.0+2` 的 APK 下下来装上去试 ——
**同一台机器、同一个崩溃**：`NoSuchMethodException:
androidx.work.impl.WorkDatabase_Impl.<init>`，点开图标什么也不发生。

也就是说：在 771a445 之前构建的**所有** release 包都打不开，
不光是本地那一份。这条推论只能靠「真的装上点一下」得到，
构建日志、安装输出里的 `Success`、以及 `flutter analyze` 都不会提示任何异常。

两个直接后果：

1. **已经下载过 v1.1.0+2 的人拿到的是一个点不开的应用**，而且因为进不去，
   它也读不到新版本 —— 只能手动重新安装。
2. **升级路径不能拿线上那份旧包来验**。因此验升级时用的是
   `git worktree add <tmp> v1.1.0+2` 从 tag 重建的版本：把
   `proguard-rules.pro` 和那两行 R8 配置补上再构建。
   **版本号刻意不改**（仍是 versionCode 2、签名也是同一把），
   这样它与 1.2.0+3 之间是真实的「覆盖安装」，升完还能顺便验
   明文库自动搬成密文那一条。

## 68. 导入完回到首页什么都没有：界面拿着一份旧快照

**需求方在真机上报的**：三批账单都导进去了、「导入记录」里也都写着**已导入**，
可首页与整理页还是「这个月还没有账单」，导入入口也还在让你「导入月账单」。

**先分清一件事：数据到底进没进库。** 杀掉应用重开 —— 首页立刻显示
¥5,780.22 / 76 笔消费。所以**写库一直是对的**，错的是界面。
这一步很关键：它把问题从「导入是不是没保存」一下子缩到了「谁没刷新」。

**根因。** 首页、整理、月报、明细读的都是 `ReviewSession` 里那**一份已经加载好的**
快照（`_snapshot` + `_report`）。而 `ImportSession.commit()` 改的是数据库，
它只更新了自己的状态与历史列表 —— 两者之间没有任何联系。于是库里有了，
界面还是旧的，直到重启才重新加载。

**为什么之前的测试没拦住。** 端到端那条导入界面测试确实走完了
「选文件 → 解析 → 核对 → 提交」，但它最后只断言了**数据库**
（`repository.dataset(ledgerId: 2)` 里有 3 笔）和提交完成页，
**没有走回首页/整理页看一眼**。「数据对」与「界面显示对了」是两件事，
这条用例只盖住了前一件。

**修法：让改账的那一方主动报信。**

* `ImportSession` 多一个 `onLedgerChanged` 回调，只在**提交成功**与
  **撤回成功**之后触发（暂存、预览、取消都不算）；
* `app.dart` 把它接到 `ReviewSession.reload()`。

**同一个坑的另一半：月份。** 光重读数据还不够 —— 用户导入的账单可能
**不是他正在看的那一个月**（比如在看 9 月、导的是 8 月的账单），那样重读之后
看到的依旧是空。所以重读时传 `followPreferredMonth: true`，让会话像**刚打开应用
那样重新判断该看哪个月**（有记录就取最新记录所在月）。这条规则的口径很干脆：

> **导入之后看到的，和重启之后看到的一模一样。**

**一个刻意的取舍：刷新失败不能说成提交失败。** 提交是事务，已经写进去了；
刷新只是界面的事。若把刷新异常冒泡上去，用户会看到「保存时出错了」
而以为要重导一遍 —— 而重复导入正是他最怕的事。所以刷新失败只打日志，
提交结果照实报成功（刷新那边的失败会由 `ReviewSession.loadError` 自己体现）。

**验证：先证明测试真的能抓住它。** 新写的那条界面用例（提交后回首页/整理页看一眼）
在两处都写了断言；把 `onLedgerChanged` 接线临时注掉再跑，它立刻变红，
报的正是真机上那句「这个月还没有账单」。然后把接线放回去 —— 全绿。
「没修之前它会不会红」这一步不做的话，测试就只是个摆设。

**顺带记一条自动化上的坑（本机环境）。** 用 `adb shell input tap` 点 Flutter 的
`YounumPressable` 时，真机上**有时会整个被丢掉**（按下与抬起几乎同刻，
手势竞技场当它没成形）。同一个坐标改用 `adb shell input swipe x y x y 140`
（按住 140ms）就稳了。本文档里那些「用 adb 走界面」的记录都按这个来。

## 69. 导入文案写「CSV / XLS / XLSX」；老式 `.xls` 大声说读不了，并给出下一步

**需求**：导入界面只写了「CSV」，实际上 csv / xls / xlsx 都能导，文案要改。

**先把事实核清（这一步不能跳）**：

* `.csv` 与 `.xlsx` 都真吃，而且是按**内容**判断、不看后缀（指南 4.2.3）；
* `app/test/账单/平安银行银行卡交易明细.xls` 的文件头是 `50 4B 03 04` ——
  它是 zip，**内容其实是 xlsx**。所以「.xls 也能导」这句话对**这一类**文件成立，
  这也是唯一一类真的验过「.xls」；
* 真正的老式 `.xls`（OLE2 容器 + BIFF 记录）读不了：工程里没有 BIFF 解析器，
  也不为它引一个（第 37 节同一个理由 —— 宁可说清，不引黑盒）。

所以文案写成「CSV / XLS / XLSX」，同时**必须**把读不了的那种说清楚。否则拿着
真 `.xls` 的用户会经历最糟的一种失败：那些字节被当文本硬解，得到一页乱码，
再被领到字段映射页**对着乱码指列** —— 看起来就像文件坏了或者应用很蠢。

**做法**：`XlsxReader.looksLikeLegacyXls()` 认 OLE2 魔数（`D0 CF 11 E0 …`），
同样按**内容**判断（改名叫 `.csv` 也认得出来），命中就拒绝，并给出
**用户做得到的那一步**：

> 这是老版本的 Excel 文件（.xls），有数读不了它。请在表格软件里「另存为」
> .xlsx 或 CSV，再把另存出来的那份导进来。

**验证（先让它红）**：把 OLE2 判断临时注掉再跑 —— 两条用例立刻变红，
失败信息正是那条乱码路的真实产物：
「分不清这份文件是 UTF-8 还是 GBK，请手工指定一次编码」。
真机上拿一个 OLE2 文件走分享入口，弹的就是上面那句话（见 `MANUAL_CHECKS.md` 十七节）。

## 70. 分享一份账单到有数：清单怎么写、来源怎么认、失败怎么说

**需求**：csv / xls / xlsx 能从系统「分享」直接进有数，应用自己判断是不是账单再解析。

**清单里的 MIME：明确的几种 + 一个 `application/octet-stream`。**
`.csv / .xls / .xlsx` 的标准类型都列了，但**多发一个 `octet-stream` 是有意的**：
很多发送方（微信分享文件就是）只知道文件名、报不出 MIME，不写这一条，
用户在最常见的那条路上**根本看不到有数**。代价是有数会出现在更多分享列表里 ——
所以真伪**不靠 MIME 判断**：内容是不是账单由解析器按内容判（指南 4.2.3），
不是账单就如实说，绝不硬导。图片、PDF、`text/plain` 没有声明，不会被误拦。

**⚠️ 顺手关掉了 deep linking（`shouldHandleDeeplinking() = false`）。**
Flutter 已默认开启 deep linking，而「用有数打开一份账单」是 `ACTION_VIEW` +
`content://` 的 intent —— 引擎会把它当成深链推进路由表，于是用户先看到一个
「未知路由 /document/1234」的页面，真正的导入反而要自己再找一遍。
这个应用的每一处跳转都是自己接的（通知走 extras、分享走文件通道），
**没有一处依赖深链**，所以关掉它没有任何损失。

**来源按内容认，认不出就当通用表格。** 分享进来的文件没有「用户选了哪个入口」
这个信息，而来源命名空间要参与同源去重键。一律记成 `manual` 的话，
「先分享一次、再从微信入口导一次」会被算成两份来源，同一个单号只能报成
「疑似重复」，用户得一组一组确认 —— 而这是同一个来源这件事本来是确定的。
所以 `ImportRules.sourceNamespaceOf()` 按识别出的平台给 `wechat` / `alipay` /
`manual`；认不出来**宁可当通用表格，不猜**（第 4.3 节那条口径：
宁可漏认、不可错认）。`sniffImportSource()` 与真正解析**共用同一段**
「字节 → 表格」代码，不会出现「认来源时说它是微信账单、解析时又当通用 CSV」。

**落地页就是「确认导入」**（需求方指定）。顺序与选文件那条路一致：
先挂解析页、再开始解析 —— 反过来解析可能先完成，用户看到的是一个停住不动的转圈。

**失败必须有人说话。** 分享这条路与选文件不同：用户是被**别的应用**唤起过来的，
失败时首页上不会有人告诉他发生了什么，他只会觉得「分享过来没反应」。
所以失败走一个只有「知道了」的提示层，把系统和文件给的原因原样说清
（真机上实测过 `open failed: EACCES (Permission denied)` 这种）。

**取走即清。** 原生侧 `pendingSharedUri` 被 Dart 取走时清空；Dart 侧回到前台
会问一次（另有 500ms 补问，因为 `onNewIntent` 有时比 `resume` 晚一步）。
不清的话每次切回应用都会重导一遍同一份文件 —— 而重复导入正是用户最怕的事。

**验证**：界面测试 6 条（成功落到确认导入页、认不出表头去映射页、老式 `.xls`
说清原因、读不了也要说清、同一份只导一次、提示层长文案 + 大字号不溢出）；
真机上 `ACTION_VIEW` + 带授权的 `content://` 冷启动走通，落到「确认导入」，
数字来自真实解析（10 月、2 笔、¥37.00）。把 `_consumeSharedFile` 临时短路再跑，
那 6 条全红。

## 71. 启动时提示新版本：一个弹层、三条路、两种不同的「不装」

**需求**：启动就检查更新；有新版本要提示；点过「忽略这个版本」就不再提示，
直到出现更高的版本。

前两条原本只有一半：`UpdateController` 启动时确实**静默**查了一次（第 64 节），
但结果只躺在「我的 → 检查更新」里 —— 用户不进那一页就永远不知道。
所以这次补的是**提示**本身，判定沿用 `UpdateRules.shouldPrompt`
（忽略过的版本不提示、出现更高版本还会提），不另起一套规则。

**三条路，其中两条必须分开**：

* 「去更新」→ 进「检查更新」页（下载仍要用户点，安装仍要系统点头，这一层没变）；
* 「忽略这个版本」→ 写进偏好，同一个版本不再打扰；
* 「以后再说」→ **什么都不记**，下次启动还会提。

合起来两条的后果是：要么用户被同一个版本反复打扰，要么他想「下次再说」
却被永久静音。语义不同就不能共用一个按钮。

**只弹一次，而且不抢用户自己查的结果**：同一次启动只弹一次（不然每次回到前台
都会弹）；用户自己点过「检查更新」时不再弹（他已经在看着结果了）。
查不到（断网、限流）依然什么都不弹 —— 第 64 节的「不打扰」口径没有变，
这条也有用例守着。

**弹层必须可滚动，这是实测出来的，不是预防性写的。**

* 更新说明是 Release 正文的**原文**，长度由发布的人决定：按真实长度的一份说明，
  不可滚动时溢出 **293px**，「以后再说」直接被挤出屏幕；
* `NoticeSheet` 的正文来自文件与系统（真机收到过一句带长路径的英文报错），
  在系统字号 2.0 下溢出 **0.273px** —— 数字虽然可笑，但它就是溢出，
  底部那个按钮跟着被挤掉；
* ⚠️ 所以滚动要包在**整块弹层外面**：`YounumSheetSurface` 里那层 Column
  给子节点的最大高度**没有扣掉顶部抓手**（22+4），子节点吃满时表面自己会溢出。
  包在里面时那 0.273px 依然在（探针打出来的 `debugCreator` 指的就是
  `Column ← Padding ← … ← YounumSheetSurface`）。

**顺手发现的一条既有问题（本轮没修）**：空首页那张装饰插画
（`start_screens.dart` 的 `_MiniReceipt`）在系统字号 2.0 下溢出 254px / 160px。
本轮只做需求里的三件事，不顺手改别人的设计；已记进 `MANUAL_CHECKS.md` 的
「已知未验证」。新加的大字号用例因此改成进演示账本，
免得那张插画把真正要验的东西淹掉。

## 72. 发 1.3.0 时 build number 取 6，而不是从 1 重新数

**发生的事情**：这一版的功能做完之后，发布时给的标签原本是 `v1.3.0+1`。

**为什么不能这么打**（不是风格问题 —— 它会把本轮刚做完的第 71 条需求直接弄失效）：

* 应用判新旧的唯一依据是 `UpdateRules.shouldPrompt` 里的 `candidateCode > currentCode`，
  而 `candidateCode` 就是标签末尾那个数字（第 64 节）。仓库已经发过
  `1.1.0+2`、`1.2.0+3`、`1.2.1+5`，用户手机上装的就是 `versionCode=5` ——
  发 `+1` 的话 `1 > 5` 不成立，**所有人都收不到更新提示**（就是第 71 节
  刚补上的那个弹层），而他们还以为自己已经是最新的。
* Android 那边同理：低 versionCode 的包不能覆盖安装高 versionCode 的包
  （`INSTALL_FAILED_VERSION_DOWNGRADE`）。想让用户装上得先卸载 ——
  而卸载会连 Keystore 里那把钥匙一起删掉，加密库就永久读不出来了。
* 仓库开了「Release 不可变」：**标签名一旦用掉就永久占用**
  （`RELEASE.md` 第 5 节记过这个坑），打错了不能改名重发，只能再换一个 build number。

**所以用 `v1.3.0+6`**：`1.3.0` 是版本名（给人看的，与需求方说的一致），
`6` 是接着上一版往下数的 build number。「1.3.0 的第一个构建」这个意思由 `+6`
表达，而不是把计数器清零。

**一件值得说清的可回退性**：这次**没有**占用 `v1.3.0+1` 这个标签名。
万一以后更想用「从 1 重新数」的口径，那个名字还空着 —— 反过来先打了 `+1`，
这个名字就被永久用掉了，而更新链在同一天就断了。

**验证**：`pubspec.yaml` 改成 `1.3.0+6` → `flutter build apk --release` →
`adb install -r` 覆盖安装 1.2.1+5：`versionCode` 5→6、`versionName` 1.2.1→1.3.0，
装完全冷启动，账目 ¥5,625.86 / 72 笔 / 3 个来源 / 整理进度 30% 与升级前**完全一致**
（这一项在 `MANUAL_CHECKS.md` 第十五节里一直标着「没验到」）。
